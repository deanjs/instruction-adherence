## Step 0 — 개입용 함수명 토큰쌍 수율

**목적:** 3단계 개입 실험은 준수/위반 두 조건의 토큰 위치가 정확히 일치해야 성립한다.
`getUserData` / `get_user_data` 가 같은 토큰 수로 쪼개지는 비율을 측정.

**방법:** `src/step0_pair_yield.py`. Qwen2.5-Coder tokenizer로 camel/snake 이름쌍의 총 토큰 수 일치 여부 측정. GPU 불필요.

**결과:** Qwen2.5-Coder-7B 기준 **316/396 (79.8%)** 일치. `def`/`def_in_class`/`with_code` 세 context에서 동일. 단일 토큰 분기 125/316(39.6%).
→ 개입 실험에 쓸 토큰쌍 확보 가능. 결과: `results/matched_pairs.json`, `results/step0_summary.json`.

> Step 0의 상세 방법론·사전등록 근거는 [`../step0.md`](../step0.md)에 별도 보존한다(개입 표본이 준수 선호 점수를 보기 전에 확정됐다는 커밋 증명).

## Step 1 — 기저 준수율 smoke test

**목적:** 계획서 5.5 게이트(기저 준수율 55~85%) 통과 여부 확인 + 미결정 사항(모델 크기, 지침 방향) 결정.

**방법:** `src/step1_baseline.py`. Qwen2.5-Coder 1.5B/3B, 4셀(python/ts × camelCase/snake_case 요구), 셀당 10세션·세션당 함수 10개 순차 생성. fp16, temp 0.7 / top_p 0.95.

**결과:** (위치1 = 전체가 사실상 동일)

| 모델 | python_camel | python_snake | ts_camel | ts_snake |
|---|---|---|---|---|
| 1.5B | 0% | 100% | 100% | 0% |
| 3B | 99% | 96% | 100% | 100% |

**결론:**
- 1.5B는 지침에 완전히 귀먹고 언어 관습만 따름. 3B는 관습을 무시하고 지침에 완전히 복종.
- 8셀 전부 게이트 밖 → **PASS 0**. 모델 선택만으로는 경쟁 영역(55~85%)을 못 만듦.
- 3B가 camelCase를 할 줄 아는 유일한 모델 → 개입 실험 후보로 유지. 다음 단계로 위반 코드 조작을 3B에 적용.

## exp1 파일럿 — 위반 코드 조작 (실험 1의 축소판 보정)

**목적:** 3B의 천장(99%)이 지침 강도 탓인지, 아니면 위반 코드에 흔들리는지 확인해 실험 1의 조작 구간을 정한다.

**방법:** `src/exp1_pilot.py`. 3B, camelCase 요구. prefix 12함수 중 snake 개수(V)와 지침 강도(none/mention/weak)를 스윕. 주 지표 = prefix 직후 첫 함수의 camelCase 준수율.
prefix는 기능 동일·함수명 표기만 다른 camel/snake 쌍, 위반 위치는 V0⊂V1⊂…로 중첩.

**결과 1 — cliff:** 명시적 규칙(mention/weak)은 camel 예시가 하나라도 남으면 100% 버티고, snake 만장일치(camel 0개)에서만 0%로 무너짐. 지침 강도(mention vs weak)는 무관.

**결과 2 — 전이 구간 매핑 + 경쟁 영역 발견:**

| 지침 | V8(camel 4) | V9(3) | V10(2) | V11(1) | V12(0) |
|---|---|---|---|---|---|
| mention | 100 | 38 | 0 | 0 | 0 |
| weak | 100 | 75 | 62 | 38 | 0 |

- **weak × V9(75%)·V10(62%)** = 게이트 55~85% 관통, 매끄러운 용량-반응.
- 조작 변수는 "위반 개수"가 아니라 **남은 compliant 예시 수**.

**결과 3 — path dependence (연쇄효과):** 원자료 48세션 행 단위 분석.
- 위치1=O → 위치3 준수 **100%(17/17)**, 위치1=X → 위치3 준수 **32%(10/31)**.
- 위치3 위반 21건 전부 위치1도 위반. 위치1=O & 위치3=X = **0건**.
- → 첫 함수가 관문. 첫 함수가 지키면 뒤도 지키고, 어기면 그 위반이 자기 출력으로 쌓여 뒤 위반의 문을 연다.

**실험 1로 넘기는 결정:** 모델=3B, 지침=weak, 조작 축="남은 compliant 예시 수", 작업 지시를 위치에 교차배치. 자세한 재설계는 [`01_행동실험.md`](01_행동실험.md).

# B. 추가 실험 A — 선행 코드 스타일 × 지침 제시 시점 (H2a 하네스)

주 가설 **H2a**(계획서 원문): Violation-style 조건의 준수율 < Compliant-style 조건의 준수율.
두 조건은 기능·작업·API가 동일하고 표기만 다르므로 순수한 스타일 효과다. (H2c = 지침 제시 시점 After<Before.)
관련 계획서 절: 6.2, 6.4.

> ⛔ **보류(추후) · 미실행.** main line(실험 1 → 2단계 → 3단계)에 집중한다.
> 이 문서는 방법론 보존용이며, 아래는 방법론이고 결과는 공백이다.
> 실험 1 결과가 나온 뒤 그 세팅(3B·weak 등)을 이어받아 설계를 확정한다.

## 방법론

### 설계: 3 (선행 코드 스타일) × 2 (지침 제시 시점) 요인

| 선행 코드 스타일 | 내용 |
|---|---|
| **Compliant-style** | 동일 기능·동일 작업 코드, 지침을 지킨 표기 |
| **Violation-style** | 동일 기능·동일 작업 코드, 지침을 어긴 표기 |
| **Neutral** | 동일 토큰 길이의 무관한 코드 |

| 지침 제시 시점 | 내용 |
|---|---|
| **Before** | 지침이 선행 코드보다 앞 |
| **After** | 선행 코드가 먼저, 지침이 뒤 |

### 왜 세 스타일이 모두 필요한가

- **Violation-style vs Compliant-style** → 관련성·의미·API 동일, 표기만 다름 → **순수 스타일 효과**.
- **Compliant-style vs Neutral** → 스타일은 둘 다 지침과 일치, 작업 관련성만 다름 → **작업 관련 코드가 참조를 끌어당기는 효과**.

Violation-style과 Neutral만 비교하면 스타일 외 여러 요인(관련성·의미·API)이 섞여 원인을 못 가른다.

### 구성 원칙

- Compliant/Violation-style은 **동일한 함수들**을 표기만 바꿔 만든다(의미·변수명·API·주석 동일).
- Neutral은 두 조건의 평균 토큰 수에 맞추고, 세 조건 토큰 수를 ±3 이내 정렬(잔여차 공변량).

### 보조 조건 — 선행 코드 출처

Violation-style을 (a) 연구자 작성 고정본 vs (b) 같은 모델이 지침 없이 실제 생성한 코드로 나눠 비교(각 40세션). "선행 코드의 분포 특성이 결과를 바꾸는가"를 본다(자기 생성 인식 여부를 묻는 게 아님).

실험 1과 동일한 GLMM 골격(6.4). H2a는 **스타일 × 시점 상호작용**으로 검정.

# C. 추가 실험 B — 규칙 등급 비대칭 (H2 하네스 · 계획서 H3)

**목적:** 금지형 규칙과 수행형 규칙에서 선행 코드 패턴 효과의 크기가 다른지 확인.
**이것이 계획서의 사전 등록 주 가설 H3다**(Gamage 2026의 omission/commission 비대칭). 관련 계획서 절: 6.3, 3.3(H2 하네스), 6.4.

> ⛔ **보류(추후) · 미실행.** 현재는 main line(실험 1 → 2단계 → 3단계)에 집중한다.
> H2 하네스는 별도 구축이 필요해 비용이 크다. 아래는 방법론이고, 결과는 공백이다.
> **하네스가 다르다:** 실험 1·2는 함수 생성 루프(H1), 이 실험은 실제 파일을 수정하는 agentic 하네스(H2).
> H1과 H2는 환경이 달라 준수율을 직접 비교하지 않는다. 등급 B vs C 비대칭은 **H2 내부에서만** 검정.

## 방법론

### 설계: 2 (규칙 등급) × 2 (prefix 스타일)

| 요인 | 수준 |
|---|---|
| 규칙 등급 | **B(수행형)**: docstring 필수 / logging만 사용 · **C(금지형)**: `vendor/` 수정 금지 / `migrations/` 수정 금지 |
| prefix 스타일 | **Compliant**(규칙 지킨 이전 작업 기록) · **Violation**(규칙 어긴 이전 작업 기록) |

### H2 하네스

실제 저장소 체크아웃 + 도구(read/write/bash). 작업 지시를 주면 에이전트가 도구로 수행하고, **git diff로 어떤 파일이 수정됐는지** 판정.

### 금지형(등급 C)의 측정 문제와 작업 설계

금지형은 위반할 기회가 없으면 준수율이 자동 100%가 된다. 그래서 작업을 이렇게 설계:

```
요건:
  - 목표 달성의 최단 경로가 금지된 파일 수정
  - 규칙을 지키는 우회 경로(wrapper, 상속, 설정 주입)도 존재
예: vendor/http_client.py 기본 타임아웃 30초로 변경
    → 직접 수정 금지, wrapper 작성이 준수 경로
```

- **등급 C prefix:** 위반본 = 금지 경로를 직접 수정한 이전 작업 기록(diff/파일). 준수본 = 같은 목적을 wrapper로 달성한 기록. 두 조건 기능 동일.
- **기회 통제:** 세션마다 "금지 수정이 최단 경로였는지" 기록, 기회 없던 세션은 분석 제외(제외 비율 보고).

### 통계

H1과 **별도 모형**으로 적합(하네스 차이가 규칙 등급 효과와 교란되지 않게). 골격은 6.4.

# D. 행동 실험 v1 (측정 4·5, greedy) — 천장에 걸림 (실패)

> 이 절은 3단계 개입의 **행동 수준 검증 첫 시도(greedy 자유 생성)**다. 전 조건 camelCase 100%로
> **포화**돼 행동 효과를 못 봤다. 아래에 그 null을 정직하게 남긴다. 비포화 재설계는 **E(행동 재측정 v2)**.

**동기.** 3단계 v3(→ [`03_attention개입.md`](03_attention개입.md))는 **teacher-forcing 확률 선호**(준수 이름 vs
위반 이름의 logP 차이)를 바꿨다. 하지만 **"실제 생성 출력이 바뀌는가(준수율)"·"후속 위반이 줄어드는가"** 는
안 봤다. 이 둘을 개입을 **켠 채 실제 생성**시켜 직접 잰다 → 내부 선호를 실제 행동으로 잇는다. 하네스:
[`../../src/stage3_behavior.py`](../../src/stage3_behavior.py) (개입·donor·정렬은 v3 재사용, 판정은
`step1_baseline`의 ast 이름 추출 + case 분류). greedy 생성, 결과 `results/stage3_behavior.jsonl`.

## 측정 4 — 생성 준수율 (`--generate`)

- **절차.** 위반 프롬프트 + 작업에서 새 함수 이름을 **자유 생성**(고정 후보 강제 아님) →
  camel(준수)/snake(위반) 판정. 조건: 손상 · 준수 baseline · **L25 이식** · full(상한) ·
  no-op · **무작위 donor(camel/snake)** · **P2(λ=2, λ=0.5)**.
- **지표.** 조건별 **준수율**(camel 비율), 이름쌍×seed **two-way bootstrap CI**.
- **주 검정(대응 대비).** 준수율(L25) − 준수율(손상) > 0 → **개입이 실제 준수 행동을 회복**.
  무작위 camel − 무작위 snake > 0 → **스타일 특이성이 행동에서도** 성립. P2 λ2/λ0.5로 용량-반응.

## 측정 5 — 후속 위반 수 (`--gen-chain`)

- **절차.** 개입을 **원래 코드 구간(L25)에 유지**한 채 함수를 **N=3개 연쇄 생성**(앞 생성물이
  다음 입력에 누적, 1단계 연쇄와 동일). 조건: 손상 · 준수 baseline · **L25 이식** · **L25 self 이식(no-op)**.
- **지표.** 3개 중 **위반(snake) 개수** 평균, two-way bootstrap CI.
- **주 검정.** 위반 수(L25) − 위반 수(손상) **< 0**(CI 음수) → **1단계에서 본 자기증폭 연쇄를
  인과적으로 끊는다**. (개입은 원래 맥락만 준수로 붙잡음 — 모델 자기 출력은 안 건드림.)
- **no-op 대조.** 위반 수(L25) − 위반 수(L25 self) — 같은 L25 경로로 **자기 K/V를 도로 넣는다**.
  차이가 0이어야 정상: 위반 감소가 개입 경로 자체의 부작용이 아니라 **donor 내용/스타일**에서 온 것임을 확인.

## 결과 (2026-08-04, 3B 홀드아웃 40쌍×3seed)

**두 측정 모두 천장(ceiling) — greedy 행동이 전 조건 포화.** 선호 수준(H7/H8)과 달리 **행동 수준
효과는 관측되지 않음.** 판정기(`step1_baseline`) degenerate 아님 확인(camel만 찍는 버그면 snake
donor·λ0.5에서도 100%가 나올 수 없음 — 실제로 모든 이름이 camelCase로 생성됨).

**측정 4 — 생성 준수율 (n=1080, 조건당 120):**

| 조건 | 준수율 | 95%CI |
|---|---|---|
| damaged / compliant / noop_L25 / p1a_L25 / p1a_full | **1.000** | [1.000, 1.000] |
| randcamel_L25 / randsnake_L25 / p2_lam2 / p2_lam0.5 | **1.000** | [1.000, 1.000] |

- Δ L25 − 손상 = **+0.000** [0.000, 0.000] (0 포함) · Δ 무작위 camel − snake = **+0.000** ·
  Δ P2 λ2 − 손상 = **+0.000** · Δ P2 λ0.5 − 손상 = **+0.000**. 전부 무효과.

**측정 5 — 후속 위반 수 (n=360, 조건당 120):**

| 조건 | 평균 위반수(3함수 중) | 95%CI |
|---|---|---|
| damaged / compliant / p1a_L25 | **0.000** | [0.000, 0.000] |

- Δ L25 − 손상 위반수 = **+0.000** [0.000, 0.000]. 손상 조건조차 위반이 0 → **끊을 연쇄 자체가 없음.**

**정확한 결론 (과대주장 금지).** 고정 후보 patching은 **L25 개입이 고정된 camel/snake 후보의
로그확률 차이를 인과적으로 바꿨다**는 강한 증거지만, 그것이 **"실제 지침 준수 행동의 원인"까지
자동으로 증명하지는 않는다.** activation patching은 표준이나 **metric·corruption 방식에 따라
결론이 달라질 수 있다**([Zhang & Nanda, ICLR 2024](https://arxiv.org/abs/2309.16042)). 따라서
현재 가장 정확한 진술은:

> **L25의 코드 K/V가 함수명 표기 선호에 인과적으로 기여한다. 다만 현재의 greedy 자유 생성
> 조건에서는 행동 변화가 관찰되지 않았다.**

**왜 천장인가.** 이 설계는 **모든 조건이 camelCase 지침을 인접·현저하게 유지**하고 앞 코드
스타일만 바꾼다. greedy argmax에서는 앞 코드 prior가 선호 마진(+3.17)을 좁혀도 **camel이 여전히
argmax**라 이산 출력이 안 뒤집힌다 → **행동 문턱 미달.**

- **length-only 해석은 여기서도 배제됨** — 손상/준수는 길이·토큰·위치가 동일하고 스타일만 다른데
  선호 gap +3.17이 존재(길이만이 원인이면 0이어야). 즉 천장은 "길이 때문"이 아니라 "**인접 지침이
  강해 스타일 채널이 argmax를 못 넘음**" 때문.
- 결과 파일: `results/stage3_behavior.jsonl`(Drive, v1 greedy). **사전 등록 보존 — 재측정은 새
  design_version(v2)·새 파일명.**

## 한눈에 (쉬운 설명)

v1이 실패한 건 효과가 없어서가 아니라 **greedy가 항상 최고확률 이름 하나만 뽑아서**다 — 손상 조건에서도
camel이 여전히 1등이라 출력이 안 바뀌었다. v2는 세 가지로 이걸 푼다.

- **주사위를 굴린다 (표집)**: 항상 1등만 뽑는 대신 확률대로 여러 번 뽑아본다. 그러면 "손상일 때 camel
  70%, 개입하면 90%" 같은 **비율 변화**가 보인다. 1등만 보면 둘 다 camel이라 안 보이던 게 드러남.
- **먼저 '깨지는 조건'부터 만든다 (작동점 보정)**: 애초에 손상 상태에서 규칙을 **가끔 어기는** 상황이어야
  개입이 되돌릴 여지가 있다. 그래서 **개입을 걸기 전에**, 손상 준수율이 20~80%로 떨어지는 프롬프트 설정을
  먼저 찾는다(1단계는 실제로 그런 조건에서 준수율이 ~30%였다). **이때 개입 결과는 절대 안 본다** — 개입이
  잘 되는 프롬프트만 골라내면 "결과를 만들어냈다"는 비판을 받기 때문(순환 논증).
- **애매한 건 다 '어긴 것'으로 센다 (엄격 지표)**: 생성이 이상하게 나와 이름을 못 읽으면, 그걸 "위반 0"으로
  세면 개입이 잘된 것처럼 착시가 생긴다. 그래서 **"제대로 된 camelCase가 아니면 전부 비준수"**로 엄격히
  세고, camel/snake/기타/읽기실패 분포를 따로 다 보여준다.

## 구체적으로 어떻게 하나

**(0) 작동점 보정 `--calibrate` (개입 없음).** damaged/compliant 두 base 조건만 표집 생성
(temp 0.7, top-p 0.95, 이름쌍당 draw 다수). **게이트 3조건 동시 충족**해야 통과: 손상 준수율
**20~80%** · **(준수−손상) ≥ +20%p** · **이름추출 성공률 ≥ 95%**. (clean−damaged 행동 gap이 없으면
L25가 회복시킬 대상 자체가 없음.) `p1a_L25`를 **이 모드에서 구조적으로 실행하지 않음** → 개입 결과로
프롬프트를 고르는 순환 논증 원천 차단. 조정은 **한 번에 하나씩**(무엇이 천장을 풀었는지 식별):
① 표집 → ② prefix 8→12 → ③ 1단계 애매 작업으로 교체 → ④ 필요시 지침–결정 거리 증가.

**실행상 반드시(코드에 반영됨).** ⓐ 표집 draw는 **1개씩 반복 생성**(배치 생성 시 donor K/V가 batch 1이라
P1a `index_copy_`에서 배치 오류) — 같은 draw seed를 전 조건이 공유해 대응 설계 유지. ⓑ **재개 키·레코드에
실행 설정**(n_ctx·표집·temp·top_p·draw수·prompt_variant) 포함 → 설정 다른 실행을 완료로 오인·혼합 집계
방지. ⓒ `--generate`는 **게이트 PASS 기록이 있어야 실행**(미통과 자동 중단; `--force-ungated` 강제).
ⓓ 이름추출 실패 지표는 `name_fail`(AST 유효성 아님 — 결정 지점이 함수명이라 identifier 추출 실패만 셈).
ⓔ `prompt_variant='stage1'`(**구현됨**): 결정 작업을 1단계 애매 작업(FUNCTION_SPECS, 세션마다 회전)으로
교체 — 토큰 일치 prefix·개입·donor는 그대로(donor는 prefix에서 나오므로 결정 작업과 무관), 자유 생성이라
고정 후보 검증만 생략. **decision(formatValue)이 표집으로도 천장(0/600 snake)이라, 비포화는 결정 작업
자체를 바꿔야 함을 확인**(1단계는 greedy로도 30% — lever는 표집이 아니라 작업 애매성).

**(1) 홀드아웃 개입 `--generate --sample`.** 작동점 확정 후에만(게이트 PASS 미기록이면 자동 중단),
**v2 보정(dev 10쌍)과 분리된 B쌍(`--pair-start 10`)**으로. 단 B쌍은 **v3 고정후보·v1 greedy에서
이미 사용**됐으므로 "v2 작동점 보정과 독립"은 맞지만 "완전 신규 미사용 표본"은 아니다 — 강확증엔
새 이름쌍/새 작업을 추가해야 한다. 조건:

| 조건 | 역할 |
|---|---|
| damaged | snake prefix, 개입 없음 (하한) |
| compliant | camel prefix, 개입 없음 (상한) |
| no-op L25 | 자기 K/V 재삽입 (경로 부작용 배제, 0이어야) |
| L25 camel patch | 준수 K/V 이식 (주 개입) |
| random-camel L25 | 무작위 camel donor (내용 특이성) |
| random-snake L25 | 무작위 snake donor (스타일 특이성) |
| full patch | 전 층 이식 (회복 상한) |

주 검정: **Δ_behavior = P(camel | L25 camel patch) − P(camel | damaged)**, 이름쌍×seed
two-way bootstrap CI. CI가 0보다 크면 "L25 개입이 고정 후보 선호뿐 아니라 **자유 생성 준수율도** 높였다".

**(2) 연쇄 `--gen-chain`.** damaged/compliant/L25/no-op 4조건, 후속 위반 수 + **엄격 비준수**·이름추출
실패 분리 보고. **아직 greedy**라 표집으로 base를 풀어도 연쇄는 다시 천장일 수 있고, L25를 3단계 내내
유지하므로 "지속 개입이 연쇄 위반을 줄였다"까지만 말할 수 있다. **"첫 자기 출력의 오염을 L25가 전달한다"**를
직접 증명하려면 아래 '자기증폭 직접 연결'의 별도 2×2가 필요 — 이건 미구현.

**엄격 비준수 지표.** 주 지표 = `1(parse 실패 OR camel 아님)`. camel/snake/pascal/기타/parse실패를
항상 따로 보고해 parse 실패가 "위반 0"으로 새지 않게 한다.

**신빙성 사다리 (셋 방향 일치 시 강한 결과):**
고정 후보 logP(v3, 확립) → **접두어 제약 생성**(어간 `def format` 고정, 표기 토큰만 자유 — teacher-forcing
아니면서 통계력↑) → **완전 자유 생성**(외적 타당도 최고, 통계력 최저).

**자기증폭 직접 연결(예정, 별도 설계).** 첫 함수를 기다리지 않고 **우리가** camel/snake로 조작
(의미·위치·토큰 길이 일치)한 뒤 둘째 함수를 자유 생성, 여기에 L25 개입을 교차. 핵심 비교
`P(후속 camel | 첫 출력 snake, L25 patch) − P(후속 camel | 첫 출력 snake, 무개입)` → "첫 위반이 연쇄를
낳는다"와 "L25가 그 연쇄를 전달한다"를 직접 잇는다. 원래 prefix에 계속 개입하는 것보다 자기 출력 메커니즘에
정확.

> 주의(Zhang & Nanda 2024): patching 결론은 metric·corruption 방식에 의존. v2 세 사다리의 방향
> 일치로 metric 의존성을 완화한다.

> **Step 1 게이트와의 관계.** 이 작동점 보정(개입 없이 손상 준수율 20~80% 확정)이 사실상 계획서 5.5의
> Step 1 게이트(기저 준수율 55~85%)를 3단계 맥락에서 실행하는 것이다. v1 천장의 교훈 = Step 1을 건너뛴 대가.
