# 01 행동실험 — 앞 코드의 위반이 다음 함수의 규칙 준수를 낮추는가 (H1a)

주 가설 **H1a**: 앞에 쌓인 위반 코드가 뒤에 만드는 함수의 규칙 준수율을 낮춘다.
관련 계획서 절: 6.1(원안), 6.4(통계), 3.3(H1 하네스).

> **이 실험은 예비실험 위에 선다.** Step 0·Step 1·exp1 파일럿([`archive_보류·실패.md`](archive_보류·실패.md#a-예비실험--실험-1을-위한-초기-실험) A절)이
> 모두 실험 1을 위한 초기 실험이었고, 그 결과로 아래처럼 설계를 잡았다.

## 한눈에 (쉬운 설명)

이 실험이 답하려는 질문은 하나다:
**"앞에 이미 규칙을 어긴 코드가 쌓여 있으면, 모델이 그다음에 만드는 함수도 규칙을 덜 지키나?"**

- **규칙**: 함수 이름을 camelCase(예: `getUserOrders`)로 써라. 이걸 어긴 게 snake_case(예: `get_user_orders`).
- **앞 코드를 우리가 만들어서 깐다**: 함수 12개짜리 코드 뭉치를 앞에 놓는다. 이 12개 중
  **규칙을 지킨(camelCase) 함수를 몇 개 남기느냐**를 조건으로 바꾼다 — 4개 남김 / 3 / 2 / 1 / 0개(전부 어김).
  나머지는 같은 함수를 snake_case로 바꿔 둔다. **함수가 하는 일은 다 똑같고 이름 표기만 다르다.**
- **그다음 새 함수를 만들게 한다**: 모델에게 새 함수 3개를 차례로 만들라 하고, 그 이름이 규칙(camelCase)을
  지켰는지 센다. 특히 **바로 다음에 오는 첫 함수**가 핵심이다.
- **왜 코드를 직접 만드나**: 실제 코드를 가져오면 표기 말고도 길이·내용·주제가 다 달라서
  "무엇 때문에 규칙을 어겼는지" 가릴 수 없다. 그래서 **다른 건 전부 똑같이 두고 '규칙 지킨 예시 수'만**
  바꾼다. 이래야 원인을 앞 코드의 표기 하나로 좁힐 수 있다.

**핵심 발견 (쉽게):**
- 규칙 지킨 예시가 **하나라도 남아 있으면** 모델은 거의 다(약 85~95%) 규칙을 지킨다.
- 그런데 예시가 **완전히 사라지면(0개)** 준수율이 갑자기 30%로 **뚝 떨어진다** — 서서히 주는 게 아니라 **절벽**처럼 급전환.
- 게다가 **첫 함수가 규칙을 어기면 그 뒤 함수들도 따라 무너진다** — 방금 자기가 어긴 이름이 다시 입력에
  쌓여 스스로를 부추긴다(자기 증폭).

## 구체적으로 어떻게 했나

(논문 방법 절의 바탕. 용어는 최대한 쉬운 말로.)

- **모델**: Qwen2.5-Coder-3B. (규칙을 지킬 줄 아는 가장 작은 모델 — 예비실험에서 확인.)
- **지침**: 시스템 메시지 끝에 **약한 어조**로 "함수 이름은 camelCase로" 한 줄. (강하게 명령하면 항상
  100% 지켜 버려서 효과가 안 보인다.)
- **앞 코드(prefix)**: 함수 12개, 크기 고정. 그중 규칙 지킨(camelCase) 함수 개수 = {4, 3, 2, 1, 0}가
  조건이고 **무작위로 배정**한다. 나머지는 같은 함수의 snake_case 버전. **어긴 함수의 위치는 무작위로
  섞어**(특정 자리에 몰리는 편향 방지) 놓는다. 조건끼리 함수 집합은 동일 — 오직 표기만 다르다.
- **생성·측정**: prefix 뒤에 새 함수를 3개 **순서대로** 만들게 한다. 앞에서 만든 함수는 다음 생성의
  입력에 그대로 쌓인다(실제 세션과 같은 상황). **주 결과 = 첫 번째 함수가 규칙을 지켰는가**(순수 직접효과).
  2·3번째는 첫 함수가 뒤를 끌고 가는지 보는 연쇄효과 보조 측정.
- **교란(원인 헷갈림) 제거**:
  - 만들 함수의 작업 지시(무슨 기능의 함수냐)를 세션마다 위치에 **돌려 배치** → "몇 번째 자리냐(위치)"와
    "무슨 작업이냐"가 섞이지 않게 분리.
  - 이름이 너무 뻔한 작업(예: 항상 `isValidEmail`)은 **제외** — 천장/바닥이라 변화를 못 잡는다.
  - camelCase와 snake_case는 토큰 길이가 달라질 수 있어, prefix의 토큰 수를 **기록해 보정**(효과가 단지
    "snake가 더 길어서"가 아님을 확인).
  - **위약 조건**: 지침 자리에 "행동을 시키지 않는, 길이만 같은 문장"을 넣어 지침 자체의 효과를 분리
    (2단계 attention 대조용).
- **통계**: 만든 함수 하나 = 관측 하나. 혼합효과 로지스틱 회귀(세션·작업을 무작위 효과로). 주 가설 H1a만
  유의성 판정, 나머지는 탐색.

## 방법론

### 원안(6.1)에서 무엇을 바꾸나 — 그리고 왜

예비실험이 밝힌 것: 3B는 camel 예시가 하나라도 남으면 규칙을 100% 지키고, **예시가 사라질 때만** 무너진다.
원안(prefix 4함수, 위반 0~3개)은 항상 camel이 1개 이상 남아 **100% 천장** → 효과가 안 보인다.
그래서 조작을 효과가 사는 구간으로 옮긴다.

| 항목 | 원안 | 재설계 | 근거(예비실험) |
|---|---|---|---|
| 모델 | 미정 | **Qwen2.5-Coder-3B** | 규칙을 지킬 줄 아는 유일한 모델 (Step 1) |
| 지침 강도 | 강(MUST) | **weak** ("Use camelCase…") | 강하면 천장 고정 (exp1 파일럿) |
| 조작 변수 | 위반 개수(0~3/4) | **남은 compliant 예시 수** (예: 3/2/1/0, prefix 12 기준) | 효과는 예시가 사라질 때 발생 |
| 작업 지시 배치 | 위치=고정 | **위치에 작업 지시 교차배치(counterbalance)** | 위치≠작업 지시 교란 제거 |
| 작업 지시 선정 | 임의 | **관용 포화 이름 배제** (예: isValidEmail) | 천장/바닥이라 민감도 0 |

**바뀌지 않는 것:** 무작위 배정, 위약 조건 + TOST, 토큰 길이 정렬(±3, 공변량), 혼합효과 로지스틱 회귀, 검정력 기반 표본 수. **주 가설 H1a도 그대로** — "선행 위반 코드가 준수율을 낮추는가"를 효과가 사는 구간에서 검정할 뿐이다.

### 설계

- **조작:** prefix(고정 크기, 예 12함수) 안의 **compliant 예시 수**를 무작위 배정 (경쟁 영역 근처: 3/2/1/0 등).
  - 네 조건의 prefix는 기능 완전 동일, 함수명 표기만 다름. 위반 위치는 무작위.
  - 토큰 길이는 주석으로 ±3 이내 정렬, 잔여차는 공변량.
- **생성:** prefix 뒤 함수 3개 순차 생성(앞 생성물이 다음 context에 누적).
- **주 결과 = 첫 번째 함수**(순수 직접효과). 2·3번째는 연쇄효과 보조(조건 × 위치 상호작용). *예비실험에서 path dependence 확인됨.*
- **작업 지시 교차배치:** 위치 1/2/3에 오는 작업 지시를 세션 간 회전시켜 위치와 작업 지시를 분리.
- **지침 종류:** 등급 A(camelCase, 개입 실험과 공유) 중심. 등급 B(docstring)는 H1 내부 참조용.

### 위약(placebo) 조건

지침 구간 attention 대조를 위해 "지침 없음" 대신 **토큰 수가 같고 행동 지시가 없는 문장**을 같은 위치에 넣는다. 위약 중립성은 **TOST 동등성 검정**(허용 ±5%p, 사전 등록)으로 확인.

### 통계 (6.4)

```
준수 여부 ~ 조건 × 후속함수순서 + prefix토큰수 + 저장소(고정효과)
          + (1 | 작업) + (1 | 세션) + (1 | 작업:seed)
```
GLMM(logit). 주 가설 H1a만 유의성 판정, 나머지 탐색적(BH 보정). 표본 수는 파일럿 검정력 분석으로 확정.

## 결과 (1차 실행: exp1_main_v1, n=20/조건, seed 1000~1019)

### dose-response (위치1 camelCase 준수율)

| compliant 남음 | 4 | 3 | 2 | 1 | 0 |
|---|---|---|---|---|---|
| 위치1 준수율 | 95% | 85% | 90% | 80% | **30%** |
| prefix 토큰(평균) | 332 | 332 | 333 | 333 | 334 |

- **H1a 지지 ✅** — compliant 4(95%) vs 0(30%), 차이 **65%p**. 위반 코드가 준수율을 낮춘다.
- **H1b(매끄러운 단조 감소) 불지지** — 4~1은 ~85%로 평평(n=20 노이즈), compliant=0에서 30%로 급락.
  매끄러운 감소가 아니라 **역치/절벽(cliff)**.
- **토큰 길이 교란 배제 ✅** — prefix 토큰 평균이 조건 간 ~332로 동일. "snake가 토큰이 더 많아서"가 아님.

### 연쇄효과 (path dependence)

| | 위치1=O → 위치2·3 | 위치1=X → 위치2·3 |
|---|---|---|
| 전 조건 공통 | 거의 100% | 붕괴 |
| compliant=0 | O(6): 위치2·3 100% | X(14): 위치2 **14%**, 위치3 **0%** |

→ **첫 함수가 관문.** 첫 위반이 자기 출력으로 context에 쌓여 뒤 함수로 자기 증폭.

### 해석

준수·위반 코드 **비율에 따른 완만한 감소**가 아니라, **준수 선례가 완전히 사라졌을 때(compliant=0)
모델이 위반 스타일로 급격히 전환**하고, 그 전환이 **후속 생성에서 자기 증폭**되는 현상이 관찰됐다.
파일럿의 매끄러운 그래디언트(100→75→62→38→0)는 **단일 작업(user_orders) 착시**였고,
작업 지시를 교차배치하니 **절벽**이 진짜 모양으로 드러났다 — 효과는 **작업 의존적**(모델이 그 이름에
대해 애매할 때만 중간 구간이 뒤집히고, 강한 관용 이름은 만장일치 위반까지 버틴다).
