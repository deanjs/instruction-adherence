# 3단계 — attention 개입 (P1a·P2)

주 가설 **H3**: attention/KV 개입이 준수 선호 점수를 **인과적으로** 바꾼다.
관련 계획서 절: 3.5(점수화), 3.6(개입). **논문의 진짜 새로움이 여기 있다.**

> 2단계는 "attention을 많이 준다"까지만 본다. 3단계는 그 attention/KV를 **직접 치환·조정**해
> 준수 결정이 바뀌는지 봄으로써 **인과 기여**를 확립한다. 오픈 모델(Qwen)에서만 가능.

---

## 한눈에 (쉬운 설명)

2단계는 "모델이 어디를 보나"까지만 봤다(상관). 3단계는 그 attention과 모델 속 앞 코드 요약값(K/V)을
**직접 바꿔치기**해서, 준수 결정이 **실제로** 바뀌는지 본다 = **원인 확인**.

- **무엇을 재나 (준수 선호 점수)**: 매 순간 모델이 **규칙 이름(`formatValue`)과 위반 이름
  (`format_value`) 중 어느 쪽을 더 선호하나**를 연속 점수로 잰다. 이진 판정(지켰다/어겼다)보다 미세한 변화를
  잡으려는 것.
- **두 개의 손잡이**:
  - **P1a**: 위반 상태(앞 코드가 snake)일 때, 모델 **특정 층의 "앞 코드 요약값(K/V)"을 준수 상태(camel)
    값으로 갈아끼운다.** → 준수 쪽으로 돌아오나?
  - **P2**: 모델이 **지침을 보는 정도(attention)를 인위로 키우거나 줄인다.** → 키우면 준수↑, 줄이면 준수↓ 인가?
- **왜 이게 '원인' 증거인가**: 앞 코드 자체나 지침 글자는 그대로 두고 **모델 속 값 딱 하나만** 바꿨는데
  결정이 바뀌면, 그 값이 **원인**이라는 뜻이다.

**핵심 발견 (쉽게):**
- **특정 층(L25)**의 "앞 코드 요약값"을 준수 값으로 바꾸면 준수가 **약 79% 회복**된다.
- 그런데 **"관계없는 아무 camel 코드"**를 넣어도 똑같이 회복되고, **snake 코드**는(내용 무관) 회복 안 된다.
  → 모델이 읽는 건 앞 코드의 **내용이 아니라 "camelCase냐 snake냐 하는 표기 스타일"**이다.
- **P2**: 지침을 보는 정도를 키우면 준수가 오르고, 줄이면 **손상보다도 더 떨어진다** — 깔끔한 반응.
  (지침 attention을 반으로 줄이면 준수 선호가 마이너스로 뒤집힘.)

## 구체적으로 어떻게 했나

(논문 방법 절의 바탕. 용어는 최대한 쉬운 말로. 아래 상세 방법론의 요약이기도 하다.)

- **채점 방식**: 앞 코드 + "새 함수 이름 후보"를 한 번에 넣어, 규칙 이름과 위반 이름 각각의 확률을
  재고 그 차이를 점수로 삼는다. 후보 두 이름은 **모든 조건에서 똑같이 고정된 문자열**을 쓴다(조건이
  달라서가 아니라 순수하게 선호가 달라진 것만 재려고).
- **개입에 쓰는 코드쌍**: camel과 snake의 **토큰 수가 정확히 같은 쌍**만 쓴다(1개만 달라도 위치가 어긋나
  값 갈아끼우기가 정의 안 됨). Step 0에서 확보한 짝을 사용.
- **P1a는 어디를 어떻게**: 모델의 앞 코드 요약값(K/V)을 **KV group 단위**로 갈아끼운다(Qwen은 여러 계산
  머리가 이 값을 공유하는 구조라, 단위를 잘못 잡으면 여러 개를 건드리며 하나로 착각한다). P2는 **계산 머리
  (query head) 단위**로 지침 보는 양에 배율(0.5·1·2·4·8)을 건다.
- **조작을 충분히 세게**: 앞 코드에 함수 한 개만 뒤집으면 차이가 거의 0이라, **여러 함수를 함께 뒤집어**
  (준수=전부 camel / 위반=전부 snake) 회복할 여지를 만든다.
- **대조군(원인 좁히기)**: ① 자기 값 그대로 넣기(변화 0이어야) ② 지침·코드 밖 구간 넣기(변화 0이어야)
  ③ **관계없는 clean 코드**를 camel·snake 두 스타일로 넣기 — 이게 "내용이냐 스타일이냐"를 가른다.
- **공정한 판정**: 설계용 파일럿은 확증에서 빼고(**홀드아웃**), 미리 정해둔 층 범위·검정 방식으로만 본다.
  숫자는 이름쌍·seed를 함께 재표본하는 **부트스트랩 신뢰구간**으로 보고, "그 신뢰구간이 0을 넘느냐"로 판정.

## 방법론

### 준수 선호 점수 (3.5)

이진 판정은 개입 실험에 너무 거칠다. 연속 점수를 쓴다.

```
준수 선호 점수 = (1/|Y_c|)·log P(Y_c | X) − (1/|Y_v|)·log P(Y_v | X)
  Y_c 준수 표기 후보(getUserOrders), Y_v 위반 표기 후보(get_user_orders), teacher forcing
```

- **후보는 조건 공통의 사전 고정 문자열.** 모델이 실제 생성한 이름에서 뽑으면 조건 간 준수 선호 점수 차이가
  선호 차이인지 문자열 차이인지 구분 불가 → **모든 조건에서 동일한 두 문자열을 채점**한다.
- 실제 생성 이름은 별도 기록해 행동 판정에만 사용(두 측정 분리).
- 보조: 정확히 한 토큰에서 갈리는 사례의 logit 차이. 길이 정규화 편향 때문에 비정규화 로그확률차도 함께 보고.

### 개입 전용 pair (3.6) — 토큰 정확 일치

행동 실험의 ±3 토큰 허용을 **여기 적용 금지.** 1토큰만 달라도 위치 인덱스·RoPE가 어긋나 K/V 치환이 정의 안 됨.
→ 두 표기의 **총 토큰 수 동일 + 결정 지점 인덱스 동일** pair만 사용(Step 0에서 316쌍 확보).

### 조작 강도 — 다중 토글 (파일럿에서 확정)

주 context pair 하나만 토글하면 준수·위반 gap이 0에 가깝다(1차 파일럿에서 확인:
손상=준수=+1.19, gap≈0). camelCase 지침이 강해 함수 1개론 결정이 안 바뀐다 —
exp1도 효과는 위반이 **다수(8~12/12)** 일 때 났다. → 주 pair + 동반 matched pair
`(n_ctx−1)`개를 **함께 토글**한다(준수=전부 camel / 위반=전부 snake). 전부 토큰정렬
pair라 정렬 유지. 동반 pool은 A/B와 겹치지 않는 고정 집합(전 세션 공통). `--n-ctx`(기본 8).
클러스터 라벨은 여전히 **주 pair**라 (이름쌍×seed) two-way 구조가 유지된다.

### 왜 지침 구간을 교체하는 건 무의미한가 (3.6)

causal mask 때문에 지침 K/V는 두 조건에서 비트 단위로 동일 → 교체해도 아무 변화 없음.
조건 간 실제로 다른 건 **① 선행 코드 구간 K/V, ② 결정 지점 query(→ 지침에 대한 α도 달라짐)** 둘뿐.
지침 `v_i`는 같으므로 `c_I` 차이는 **오직 α 때문** — 이게 개입 설계를 결정한다.

### 네 가지 개입 — GQA 단위 주의

실제 실행 모델 **Qwen2.5-Coder-3B-Instruct**는 GQA(query head 16, KV head 2, **8:1 공유** — KV head
하나를 query head 8개가 공유). 층당 수는 아래 표 기준. (head 수는 모델 config에서 읽으므로 실행 코드는
자동으로 맞음 — 7B로 바꾸면 28/4/7:1이 된다. 단위 원칙은 크기 무관.)

| 개입 | 조작 대상 | 단위 | 층당 수(3B) |
|---|---|---|---|
| **P1a (주)** | query 고정, 코드 구간 K/V를 준수 실행 값으로 치환 후 α 재계산 | **KV group** | **2** |
| **P2 (보조)** | 위반 조건 내부에서 지침 구간 α에 배율 λ∈{0.5,1,2,4,8} (PASTA 계열, 양-반응) | query head | 16 |
| P1b (탐색) | 코드 구간 기여분 `c_C` 이식 | query head | 16 |
| P3 (탐색) | 지침 구간 기여분 `c_I` 교차 교체 | query head | 16 |

- **P1a를 query head 단위로 짜면 안 됨** — K/V는 group 내 8개 head가 공유하므로, 실제론 8개를 건드리면서 1개로 보고하게 됨. **P1a는 KV group 2개** 단위로 순회.
- 개입은 후보 함수명의 **모든 teacher-forcing step**에 동일 적용 후 sequence 수준 준수 선호 점수 계산(보조: 첫 토큰만).
- 질량 보존 변형을 주 결과(배분 변화만 분리), 비보존은 총량 변화 공변량으로 보고.

### 개입 효과 판정 (3.6)

- **주 지표 준수 선호 점수 변화량** = `개입본 준수 선호 점수 − 손상본 준수 선호 점수`. **준수 선호 점수로 표본을 선별하지 않는다**(순환 논증·평균 회귀 오독 방지). 선별 기준은 토큰 수 일치·함수명 속성·명세 슬롯 등 준수 선호 점수 무관 사전 기준만.
- **표본 분할:** A(50쌍)=기저 준수 선호 점수 변화량 추정 전용, B(50쌍)=개입 실행. Recovery Ratio = B의 준수 선호 점수 변화량 ÷ A의 기저 준수 선호 점수 변화량(분자·분모 상관 회피).
- **음성 대조**(효과가 **없어야** 함): no-op patch, 무관 구간 patch, R 구간 patch, 무작위 단위 patch.
  → 무작위 개입 준수 선호 점수 변화량 분포를 **귀무분포**로, P1a가 상위 꼬리인지 검정(**주 판정 기준**).
- 순회: P1a = 전 층 × KV group 2, P2 = 전 층 × query head 16. 음성 대조도 동일 범위.

### 절대 규칙 (완화 금지)

1. 준수 선호 점수 값으로 표본 선별 금지. 2. 후보는 전 조건 동일 문자열. 3. 개입 pair 토큰 수 정확 일치.
4. P1a는 KV group(3B 2개), P2/P1b/P3는 query head(3B 16개). 5. 주 가설은 H3.

### 주 조건과 귀무분포 (리뷰 반영)

- **주 개입 = `p1a_L25_allG`** — 2단계 split-half로 재현된 **L25 단독 × 전 KV group**에
  코드 K/V를 준수 값으로 이식. "L25가 준수 결정의 원인인가"를 직접 검정.
- **층별 개입** — 전 층 각각을 같은 규모(1층×전 group)로 돌려 `p1a_L{li}_allG`. 주 검정은
  아래 "확증 분석 계획"의 **대응 대비**(후기 층 평균·무작위 donor 대비)로 하고, 층별 순위는
  민감도로만 본다(전 층 순위는 초기 층 전파로 오염, 순위 p는 바닥 존재).
- **회복 상한** = `p1a_full`(전 층×전 group). Recovery Ratio 분자 상한.
- **단계적 범위(보조)** — 원인이 이름 토큰인지 이후 전파 표현인지 구분:
  `p1a_L25_name`(context 이름 토큰만) ⊂ `p1a_L25_func`(함수 전체) ⊂ `p1a_L25_allG`(선행 코드 전체).
- **대조**:
  - **무작위 donor**(`ctl_randdonor_L25` camel · `ctl_randdonor_snake_L25` snake) — 같은 L25·
    같은 위치·같은 토큰 수에 **비동일 clean K/V**(다른 pair들, 길이 일치). camel은 내용
    특이성(①a), camel↔snake 대비는 스타일 특이성(①b) 검정에 쓴다.
  - **동일 영역**(전부 조건 간 동일 → Δ≈0, 배관 검증): `ctl_noop`(donor=self, 정확 0)·
    `ctl_instr`(지침, 비트 동일)·`ctl_boiler`(코드 밖 보일러플레이트). 다중 토글에선 코드
    블록 전체가 조건 간 다르므로 단일 토글 때의 prectx/postctx는 오염돼 폐기.
- **P2** = 지침 α×λ. 전 층×전 head λ 곡선(**단조 추세 Spearman**) + 전 층 국소(층별 귀무).

### 통계 — two-way cluster bootstrap

- config당 (이름쌍, seed) 셀에 관측 1개뿐이라 (pair,seed) 단일 클러스터 재표본은 사실상
  iid라 반복 구조를 못 담는다. 그래서 **이름쌍 50개와 seed 3개를 각각 독립 복원추출**하고
  교차셀 평균을 통계로 쓴다(crossed two-way). 이게 이름쌍·seed 무선효과를 반영해 CI를
  적정하게 넓힌다(합성 검증: iid 폭의 약 3배).
- **주 유의성 = L25 Δ의 two-way 부트 95% CI가 0을 배제하는가** + 대조=0 + 단계 용량-반응.
- Recovery Ratio는 분자(B config)·분모(A gap)의 **독립 two-way 부트 분포**를 짝지어 비율 CI.
- P2 λ 단조성 = λ vs 평균 Δ의 Spearman ρ.

### 확증 분석 계획 (사전 등록, v3) — 파일럿 교훈 반영

**v2 파일럿에서 발견:** 단일 층 K/V 이식은 **downstream 전파**돼, 입력에 가까운 초기 층을
건드리면 사실상 코드를 통째로 교체한 셈이라 자명히 full 회복이 된다(`p1a_L0 ≈ p1a_full`).
초기 층의 양·음 전파도 관측됨(L2·L3 음수). → **전 층 교환가능성(exchangeability) 가정이
위배**될 수 있다. 순위 기반 p는 바닥 1/(귀무 층수+1)이라 후기 11~18층으로도 0.05 미만 불가.

이에 다음을 **사전 등록**한다:

1. **파일럿(v2, B pair 앞 `PILOT_PAIRS=10`쌍) 분리** — 설계용으로만 쓰고 확증서에서 제외.
   확증은 **홀드아웃**(`--pair-start 10`, design_version=v3)에서만.
2. **후기 층 범위 사전 고정** = 모델 마지막 1/3(구조 기준, 결과 무관; 36층이면 L24~L35).
   L25 주변 임의 선택 금지.
3. **주 검정 = 대응 대비의 two-way bootstrap 95% CI가 0을 배제하는가**(순위 p 아님):
   - **①a 내용 특이성:** Δ(L25 준수 donor) − Δ(**L25 무작위 camel donor**) > 0.
     무작위 donor = 같은 L25·같은 위치·같은 토큰 수에 **비동일 clean K/V**(다른 pair들, camel).
     >0면 준수-코드 **내용**이 특이적. ≈0/음수면 내용 무관(camel이면 뭐든 회복).
   - **①b 스타일 특이성:** Δ(무작위 **camel**) − Δ(무작위 **snake**) > 0. 내용은 같은 무작위로
     고정하고 **case만** 다르게 → camelCase **스타일**이 회복을 구동하는지 분리.
     ①a≈0·①b>0 = "내용 아닌 case-스타일 특이", ①a>0 = 내용 특이, 둘 다≈0 = 아무 코드.
   - **② 층 특이성:** Δ(L25) − mean(사전 고정 후기 층 제외본) > 0.
   - **③ 회복:** Δ(L25 준수 이식) > 0.
4. **민감도 분석:** 기존 전 층 순위·후기 순위 p를 삭제하지 않고 그대로 보고(검정 아님, 순위 근거).
5. **탐색:** L0의 강한 회복, 초기 층 양·음 전파 효과.

> 논문 기술: "파일럿에서 초기 층 개입의 downstream propagation으로 전 층 교환가능성 가정이
> 위배될 수 있음을 발견하여, 파일럿 표본을 확증 분석에서 제외하고 사전 정의된 후기 1/3 층을
> 대상으로 L25와 후기 층 평균의 대응 대비 및 비동일 무작위 donor 대비를 주 검정으로 등록,
> 기존 전 층 순위 분석은 민감도 분석으로 유지하였다."

### 하네스가 절대 규칙을 강제하는 방식

- **규칙 1:** A/B 분할은 고정 seed 셔플만 — 준수 선호 점수를 선별에 절대 참조 안 함.
  Recovery Ratio 분자(B)·분모(A)는 분리 표본.
- **규칙 2:** 결정 후보는 **작업과 의미가 맞는 고정 쌍** `formatValue`/`format_value`(camel=준수).
  모든 조건·개입에서 동일 채점. 실제 생성 이름은 이 스크립트에서 안 씀(측정 분리).
- **규칙 3:** `prepare_session`이 준수/위반 프롬프트를 대조, **코드 구간 밖 상이 시 폐기**.
  후보 토큰이 조건에 의존하면(`cand_context_dependent`) 폐기.
- **규칙 4:** P1a는 pre-repeat `key/value`의 `kvh` 축(=KV group)을 `index_copy_` 치환 —
  group 내 공유 query head를 함께 건드림이 자명. P2는 post-softmax α의 `H` 축(=query head).
  V4가 `n_q % n_kv == 0` 정합과 head 수를 보고(1.5B은 12×2, 개입 3B은 실제 head 수 사용).
- **규칙 5:** 출력은 새 파일 `stage3_intervention.jsonl`. 기존 `results/`는 불변.

### 개입 메커니즘 메모

- **채점은 전체 시퀀스 정사각 forward**로 한다(`[프롬프트 + 후보]` 한 번에). 캐시 재사용
  (`past_key_values`)은 query 길이≠key 길이에서 SDPA `is_causal`이 좌상단 정렬로 오정렬돼
  후보가 prefix를 못 봤다(파일럿에서 gap=0·V7=0로 드러남). 정사각 forward는 그 문제가 없다
  (V1로 검증). **Colab의 "prefix 캐시 1회 재사용" 최적화는 정확성을 위해 포기** — P2 대규모
  스윕 속도는 이후 별도 최적화(예: prefill 은닉상태 캐시).
- 개입은 그 forward 안에서 적용: P1a는 코드 구간 `key/value` 열을 준수본 donor로 덮어쓰고
  (모든 teacher-forcing step 자동), P2는 지침 α에 λ(질량 보존 시 재정규화). donor는 준수
  prefill 캐시의 해당 위치 슬라이스(임의 위치 지원 → 대조군도 같은 경로).
- **P1b/P3(탐색)는 v1/v2 미구현** — 주 가설 H3(P1a)에 집중. 기여분 분해 이식은 후속 별 파일.

## 행동 실험 — 개입 아래 실제 생성 (측정 4·5)

**동기.** 위 v3는 **teacher-forcing 확률 선호**(준수 이름 vs 위반 이름의 logP 차이)를 바꿨다.
하지만 **"실제 생성 출력이 바뀌는가(준수율)"·"후속 위반이 줄어드는가"** 는 안 봤다. 이 둘을
개입을 **켠 채 실제 생성**시켜 직접 잰다 → 내부 선호를 실제 행동으로 잇는다. 하네스:
[`src/stage3_behavior.py`](../../src/stage3_behavior.py) (개입·donor·정렬은 v3 재사용, 판정은
`step1_baseline`의 ast 이름 추출 + case 분류). greedy 생성, 결과 `results/stage3_behavior.jsonl`.

### 한눈에 (쉬운 설명)

앞의 v3까지는 모델의 **속마음(어느 이름을 더 좋아하나 하는 점수)**만 바꿨다. 여기서는 개입을 **켠 채로
모델이 실제로 함수 이름을 써내게** 해서, 겉으로 나오는 결과까지 바뀌는지 두 가지로 확인한다.

- **측정 4 — 실제로 규칙을 지킨 이름이 나오나 (준수율)**: 위반 상태(앞 코드가 snake)에서 새 함수 이름을
  **자유롭게 쓰게** 하고, 나온 이름이 규칙 표기(camelCase)인지 위반 표기(snake_case)인지 센다. 개입을
  걸었을 때 규칙 표기 비율이 실제로 오르면, 속마음뿐 아니라 **실제 출력**까지 바뀐 것이다.
- **측정 5 — 한 번 어기면 계속 어기는 연쇄를 끊나 (후속 위반 수)**: 함수를 **연달아 3개** 쓰게 하되, 앞에
  쓴 함수가 다음 입력에 그대로 쌓이게 둔다(1단계에서 본 "한 번 어기면 뒤도 따라 어기는" 상황 재현). 개입을
  원래 앞 코드 자리에만 계속 걸어두고, 뒤따라 나오는 3개 중 **위반이 몇 개**인지 센다. 손상 상태보다 위반이
  줄면, 그 자기증폭 연쇄를 **원인 수준에서 끊는다**는 뜻이다.
- **속지 않으려는 장치**: 두 측정 다 규칙 표기가 원래 흔한 게 아니라 **개입 때문에** 바뀐 것임을 못 박으려고,
  ① 자기 값을 도로 넣기(변화 0이어야) ② 관계없는 camel/snake 코드 넣기(내용이냐 스타일이냐 가르기)
  ③ 지침 보는 양을 키우고/줄이기(P2) 같은 대조를 함께 돌린다. 결과가 안 바뀌면 정직하게 "속마음 수준에
  한정"으로 축소해 적는다(실제 프로젝트 코드에서의 재현은 별개 후속 과제).

### 구체적으로 — 측정 4: 생성 준수율 (`--generate`)

- **절차.** 위반 프롬프트 + 작업에서 새 함수 이름을 **자유 생성**(고정 후보 강제 아님) →
  camel(준수)/snake(위반) 판정. 조건: 손상 · 준수 baseline · **L25 이식** · full(상한) ·
  no-op · **무작위 donor(camel/snake)** · **P2(λ=2, λ=0.5)**.
- **지표.** 조건별 **준수율**(camel 비율), 이름쌍×seed **two-way bootstrap CI**.
- **주 검정(대응 대비).** 준수율(L25) − 준수율(손상) > 0 → **개입이 실제 준수 행동을 회복**.
  무작위 camel − 무작위 snake > 0 → **스타일 특이성이 행동에서도** 성립. P2 λ2/λ0.5로 용량-반응.

### 구체적으로 — 측정 5: 후속 위반 수 (`--gen-chain`)

- **절차.** 개입을 **원래 코드 구간(L25)에 유지**한 채 함수를 **N=3개 연쇄 생성**(앞 생성물이
  다음 입력에 누적, 1단계 연쇄와 동일). 조건: 손상 · 준수 baseline · **L25 이식** · **L25 self 이식(no-op)**.
- **지표.** 3개 중 **위반(snake) 개수** 평균, two-way bootstrap CI.
- **주 검정.** 위반 수(L25) − 위반 수(손상) **< 0**(CI 음수) → **1단계에서 본 자기증폭 연쇄를
  인과적으로 끊는다**. (개입은 원래 맥락만 준수로 붙잡음 — 모델 자기 출력은 안 건드림.)
- **no-op 대조.** 위반 수(L25) − 위반 수(L25 self) — 같은 L25 경로로 **자기 K/V를 도로 넣는다**.
  차이가 0이어야 정상: 위반 감소가 개입 경로 자체의 부작용이 아니라 **donor 내용/스타일**에서 온 것임을 확인.

### 결과 (2026-08-04, 3B 홀드아웃 40쌍×3seed)

**두 측정 모두 천장(ceiling) — greedy 행동이 전 조건 포화.** 선호 수준의 H3와 달리 **행동 수준
효과는 관측되지 않음.** 판정기(`step1_baseline`) degenerate 아님 확인(camel만 찍는 버그면 snake
donor·λ0.5에서도 100%가 나올 수 없음 — 실제로 모든 이름이 camelCase로 생성됨).

**측정 4 — 생성 준수율 (n=1080, 조건당 120):**

| 조건 | 준수율 | 95%CI |
|---|---|---|
| damaged / compliant / noop_L25 / p1a_L25 / p1a_full | **1.000** | [1.000, 1.000] |
| randcamel_L25 / randsnake_L25 / p2_lam2 / p2_lam0.5 | **1.000** | [1.000, 1.000] |

- Δ L25 − 손상 = **+0.000** [0.000, 0.000] (0 포함) · Δ 무작위 camel − snake = **+0.000** ·
  Δ P2 λ2 − 손상 = **+0.000** · Δ P2 λ0.5 − 손상 = **+0.000**. 전부 무효과.

**측정 5 — 후속 위반 수 (n=360, 조건당 120):**

| 조건 | 평균 위반수(3함수 중) | 95%CI |
|---|---|---|
| damaged / compliant / p1a_L25 | **0.000** | [0.000, 0.000] |

- Δ L25 − 손상 위반수 = **+0.000** [0.000, 0.000]. 손상 조건조차 위반이 0 → **끊을 연쇄 자체가 없음.**

**정확한 결론 (과대주장 금지).** 고정 후보 patching은 **L25 개입이 고정된 camel/snake 후보의
로그확률 차이를 인과적으로 바꿨다**는 강한 증거지만, 그것이 **"실제 지침 준수 행동의 원인"까지
자동으로 증명하지는 않는다.** activation patching은 표준이나 **metric·corruption 방식에 따라
결론이 달라질 수 있다**([Zhang & Nanda, ICLR 2024](https://arxiv.org/abs/2309.16042)). 따라서
현재 가장 정확한 진술은:

> **L25의 코드 K/V가 함수명 표기 선호에 인과적으로 기여한다. 다만 현재의 greedy 자유 생성
> 조건에서는 행동 변화가 관찰되지 않았다.**

**왜 천장인가.** 이 설계는 **모든 조건이 camelCase 지침을 인접·현저하게 유지**하고 앞 코드
스타일만 바꾼다. greedy argmax에서는 앞 코드 prior가 선호 마진(+3.17)을 좁혀도 **camel이 여전히
argmax**라 이산 출력이 안 뒤집힌다 → **행동 문턱 미달.**

- **length-only 해석은 여기서도 배제됨** — 손상/준수는 길이·토큰·위치가 동일하고 스타일만 다른데
  선호 gap +3.17이 존재(길이만이 원인이면 0이어야). 즉 천장은 "길이 때문"이 아니라 "**인접 지침이
  강해 스타일 채널이 argmax를 못 넘음**" 때문.
- 결과 파일: `results/stage3_behavior.jsonl`(Drive, v1 greedy). **사전 등록 보존 — 재측정은 새
  design_version(v2)·새 파일명.**

**행동 효과를 실제로 보기 위한 설계(진행 중, 아래 "행동 재측정 v2" 절).** 핵심은 **1단계의
비포화 조건을 3단계로 가져오기**다 — 1단계는 전부 위반 prefix에서 첫 함수 준수율이 ~30%였다(천장
아님). 순서: (1) **표집**(temp 0.7, top-p 0.95)으로 준수율을 rate화 — 가장 쌈. (2) 여전히 포화면
**prefix 12개·1단계 애매 작업**으로 손상 기저 준수율 20~80% 작동점을 **개입 없이** 확정(개입 결과
보고 프롬프트 고르면 순환 논증 — `p1a_L25`는 이 단계에서 절대 안 봄). (3) 작동점 고정 후 **새
홀드아웃**에서 L25/no-op/무작위 camel/무작위 snake/full 비교, 주 검정 Δ=P(camel|L25 camel patch)
− P(camel|damaged). (4) 완전 자유 생성이 계속 포화면 **접두어 제약 생성**(어간 고정 `def format`,
표기 토큰만 모델이 생성)으로 통계력↑. 신빙성 순서 = 고정 후보 logP → 접두어 제약 생성 → 완전 자유
생성; 셋의 방향이 같으면 강한 결과.

### 2026-08-04 — H3 확증: L25는 선행 코드의 case-스타일을 인과적으로 읽는다
