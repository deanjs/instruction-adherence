## 1. 연구 주제

### 1.1 배경

Claude Code, Codex 같은 코딩 에이전트는 저장소에 놓인 `AGENTS.md` / `CLAUDE.md`를 읽고 그 안의 규칙을 따르도록 설계되어 있다. "함수 이름은 camelCase로 쓴다", "`vendor/` 아래 파일은 건드리지 않는다" 같은 프로젝트 규약이다.

그런데 이 규칙이 세션 내내 지켜지지 않는다는 보고가 있다. McMillan(2026)은 Claude Code 세션 1,650건을 분석해 **함수를 하나 더 생성할 때마다 규칙 준수의 odds가 약 0.944배가 된다**고 보고했다.

> **odds ratio 해석에 관하여**
> 이 수치는 준수 확률이 5.6%p 떨어진다는 뜻이 아니다. odds는 `p/(1−p)`이므로 같은 odds ratio라도 기준 준수율에 따라 확률 변화량이 다르다. 준수율 90%에서 한 단계 진행하면 약 89.5%, 50%에서는 약 48.6%가 된다. 본 연구는 효과 크기를 odds ratio로 보고하고, 확률로 환산할 때는 기준 준수율을 항상 함께 명시한다.

같은 연구는 파일 크기, 지침 위치, 파일 분할 구조, 인접 파일과의 상충 여부 등 **구조적 요인이 준수율에 감지 가능한 영향을 주지 않는다**는 것도 함께 보고했다. 즉 하락은 관찰되지만 원인은 열려 있다.

Gamage(2026)는 일반 대화에서 유사한 현상을 확인하고, "에이전트가 스스로 만들어낸 내용이 이 현상에 기여하는지는 현재 설계로 분리할 수 없으며 미해결 문제"라고 명시했다.

### 1.2 연구 대상의 정확한 정의

모델은 context에 들어 있는 코드가 자신이 생성한 것인지, 사람이 작성한 것인지 구분할 수 없다. 입력으로는 동일한 토큰열일 뿐이다.

따라서 본 연구가 다루는 것은 엄밀히 말해 "자기 생성 여부"가 아니라 **"context에 누적된 선행 코드 패턴"**이다.

이 구분은 처방에도 영향을 준다. 자기 생성이 문제라면 에이전트의 생성 방식을 바꿔야 하지만, 누적된 패턴이 문제라면 그 코드의 출처와 무관하게 context 관리가 답이 된다.

### 1.3 어떤 인과 구조를 의심하는가

코딩 에이전트가 쓰는 언어 모델은 decoder-only 구조다. 여기서 두 성질이 나온다.

- 생성은 왼쪽에서 오른쪽으로만 진행되며, 이미 만든 것을 되돌아가 고칠 수 없다
- **생성된 결과가 즉시 다음 생성의 조건이 된다**

두 번째 성질에 주목하면 다음 경로를 세울 수 있다.

```
코드가 생성됨
   ↓
그 코드가 context에 누적
   ↓
이후 토큰 생성 시 그 코드를 참조
   ↓
지침보다 선행 코드에 맞춘 출력
   ↓
지침 준수율 하락
```

같은 계열의 현상이 다른 도메인에서 보고되어 있다. Zhang et al.(ICML 2024)의 hallucination snowballing은 모델이 한 번 잘못된 사실을 말하면 이후 토큰이 그 오류에 정렬된다는 것을 보였다. 본 연구는 이 메커니즘이 **사실 오류가 아니라 규칙 위반에 대해서도, 코딩 에이전트라는 맥락에서도 성립하는지** 검증한다.

> **단정하지 않는 것**
> 본 연구는 "decoder-only 구조 자체가 지침 무시의 원인이다"라고 주장하지 않는다. 구조는 가설을 세운 출발점이며, 다른 구조와의 비교 실험을 하지 않으므로 구조를 원인으로 지목할 근거가 없다.

### 1.4 왜 관찰만으로는 답할 수 없는가

가장 흔한 접근인 "첫 위반 시점 전후 준수율 비교"는 성립하지 않는다.

```
함수 순서:  1    2    3    4    5    6    7    8
준수 여부:  O    O    O    X    O    X    X    O
                          ↑ 첫 위반

첫 위반 이전 준수율 = 3/3 = 100%
첫 위반 이후 준수율 = 3/5 = 60%
```

**"첫 위반"의 정의상 그 이전 구간의 준수율은 항상 100%다.** 따라서 "이후가 낮다"는 결과는 어떤 데이터를 넣어도 반드시 나온다. 발견이 아니라 정의의 산물이다.

여기에 두 문제가 더 얹힌다.

- **선택 편향** — 첫 위반이 일찍 나온 세션과 늦게 나온 세션은 작업 난이도가 다르다
- **역인과** — 위반이 위반을 부른 것이 아니라 어려운 작업이라 위반이 여러 번 나왔을 수 있다

그래서 본 연구는 **위반하기를 기다리지 않고 context를 직접 만들어 무작위 배정한다.**

## 2. 무엇을 실험하는가

### 조작 1 — context 안의 위반 코드

context에 규칙을 어긴 코드가 들어 있으면 다음에 생성되는 코드의 준수율이 낮아지는가?

준수 코드와 위반 코드는 **기능이 동일하고 규칙 준수 여부만 다르게** 만든다. 무작위 배정하므로 준수율 차이는 "context에 위반 코드가 있다"의 인과 효과다.

### 조작 2 — 선행 코드 스타일과 지침 제시 시점

두 요인을 교차한다.

- **선행 코드 스타일** — 같은 작업의 준수 스타일 / 같은 작업의 위반 스타일 / 같은 길이의 무관한 코드
- **지침 제시 시점** — 선행 코드보다 앞 / 선행 코드보다 뒤

앞의 두 스타일 조건은 기능·작업·API·변수명을 모두 동일하게 두고 표기만 다르게 만든다. 무관한 코드와만 비교하면 "스타일 때문인지, 작업 관련 코드가 더 강하게 참조되기 때문인지" 구분할 수 없기 때문이다.

### 조작 3 — attention 구성요소

위 효과가 실재한다면, **선택한 attention component가 해당 행동 효과에 인과적으로 기여하는가?**

> 이 질문은 "행동 효과의 몇 퍼센트가 attention 경로를 지나는가"와 다르다. 후자는 전체 효과를 경로별로 분해할 수 있어야 답할 수 있으나, 본 연구의 개입은 특정 층·특정 구간에 한정된 국소 개입이다. 답할 수 있는 것은 **"이 구성요소가 기여하는가, 그 크기는 얼마인가"**까지다.

## 3. 어떻게 실험하는가

### 3.1 3단 구조

각 단계는 앞 단계에 의존하지만, 앞 단계만으로도 독립적인 결과가 성립한다.

| 단계 | 내용 | 산출 | 실패 시 |
|---|---|---|---|
| **1단계** | 통제된 context 조작 | 행동 수준 인과 효과 추정치 | — (논문의 본체) |
| **2단계** | 길이 정규화 attention 관측 | 조건 간 attention 배분 차이 | 1단계만으로 성립 |
| **3단계** | attention 개입 | attention 구성요소의 인과 기여 | 1·2단계만으로 성립 |

### 3.2 어떤 규칙을 대상으로 하는가

규칙 종류에 따라 필요한 실행 환경과 측정 가능한 층위가 다르다.

| 등급 | 규칙 유형 | 예시 | 하네스 | 행동 | 개입 |
|---|---|---|---|---|---|
| **A** | 표기 규약 (결정 지점 국소) | 함수명 camelCase | H1 | 가능 | **가능** |
| **B** | 수행형 (commission) | docstring 필수, logging만 사용 | H1, H2 | 가능 | 불가 |
| **C** | 금지형 (omission) | 특정 경로 수정 금지 | **H2 전용** | 가능 | 불가 |

**등급 A가 개입 실험을 담당하는 이유**

개입 효과를 재려면 준수/위반이 짝을 이루는 후보열이 있어야 준수 선호 점수를 정의할 수 있다(3.5). `getUserData` / `get_user_data`처럼 같은 의미를 두 표기로 쓸 수 있는 규칙만 이 조건을 만족한다.

**등급 C를 반드시 포함하는 이유**

표기 규약만 다루면 두 문제가 생긴다.

첫째, 실무 타당도가 낮다. 실제 `AGENTS.md`에서 비중이 큰 것은 서식이 아니라 제약이다. "생성된 파일은 편집하지 말 것", "`vendor/` 아래는 건드리지 말 것" 같은 규칙이며, 어겼을 때 손실도 크다.

둘째, 이론적으로 다른 종류일 수 있다. Gamage(2026)는 **금지형 지침은 대화가 길어질수록 무너지지만 수행형 지침은 유지된다**는 비대칭을 보고했다. 이 비대칭이 선행 코드 패턴 효과에도 나타나는지는 별도의 질문이며, 나타난다면 두 문헌을 잇는 결과가 된다.

**등급 C 규칙**

| 규칙 | 문구 | 판정 |
|---|---|---|
| 외부 코드 보호 | "`vendor/` 아래 파일은 수정하지 말 것. 필요하면 wrapper를 만들 것" | 해당 경로 diff 발생 여부 |
| 생성 파일 보호 | "`*_pb2.py`, `migrations/` 아래는 수정 금지" | 해당 경로 diff 발생 여부 |

### 3.3 두 개의 하네스

등급 C는 실제로 파일을 수정할 수 있는 환경이 아니면 위반 자체가 불가능하다. 명세 기반 생성 루프에는 파일 시스템 조작이 없으므로 "수정 금지" 규칙을 표현할 수 없다. 따라서 하네스를 둘로 나눈다.

#### H1 — 명세 기반 함수 생성 루프 (등급 A, B)

```
반복:
  1. 미리 준비한 함수 명세를 제시
     ("사용자 ID로 주문 목록을 조회하는 함수를 작성하라")
  2. 모델이 함수 하나를 생성
  3. 생성 결과를 context에 추가
  4. 다음 명세로 이동
```

- 명세 목록은 조건 간 동일하게 고정
- 탐색·도구 호출·실패 재시도가 없어 조작 이외의 변동이 제거됨
- **attention 관측과 개입이 가능한 유일한 하네스** (생성 위치가 결정론적으로 특정됨)

#### H2 — 파일 편집 agentic 하네스 (등급 B, C)

```
환경:
  실제 저장소 체크아웃
  vendor/, migrations/, 외부 기여 모듈이 실제로 배치됨
  도구: read, write, bash

반복:
  1. 작업 지시를 제시
     ("vendor/http_client.py의 기본 타임아웃을 30초로 바꿔라")
  2. 에이전트가 도구를 써서 작업 수행
  3. git diff로 어떤 파일이 수정됐는지 판정
```

- 금지형 규칙을 표현할 수 있는 유일한 환경
- 대신 완주 실패, 탐색 경로 차이 등 변동이 크다
- 행동 측정만 수행. attention 관측·개입은 하지 않는다

#### 하네스 간 비교의 제약

H1과 H2는 환경이 다르므로 **두 하네스의 준수율을 직접 비교할 수 없다.** 등급 B와 C의 비대칭(Gamage 비교)을 검증하려면 같은 하네스 안에서 비교해야 한다.

따라서 **H2에 등급 B 규칙과 등급 C 규칙을 모두 배치**하고, 비대칭 검정은 H2 내부에서만 수행한다. H1의 등급 B는 H1 내부 참조용이다.

```
등급 B vs C 비대칭 검정  →  H2 내부에서만
등급 A 개입 실험         →  H1에서만
```

#### 금지형 규칙의 측정 문제

금지형 규칙은 **위반할 기회가 없으면 준수율이 자동으로 100%가 된다.** 따라서 H2의 작업을 다음 조건으로 설계한다.

```
작업 요건:
  - 목표 달성의 최단 경로가 금지된 파일을 수정하는 것
  - 동시에 규칙을 지키는 우회 경로(wrapper, 상속, 설정 주입)도 존재
```

**기회 지표:** 세션마다 "금지된 수정이 최단 경로였는지"를 기록하고, 기회가 없었던 세션은 분석에서 제외한다. 제외 비율을 보고한다.

### 3.4 attention을 어떻게 꺼내는가

전체 attention matrix 저장은 불가능하다. Qwen2.5-Coder-7B(약 28개 층, query head 28개, KV head 4개 — 정확한 값은 `config.json`에서 확인)에서 context 16K일 때 prefill 단계 attention matrix는 다음과 같다.

```
한 층:    16,384 × 16,384 × 28 heads × 2 bytes ≈ 15 GB
전체 층:  15 GB × 28 ≈ 420 GB
```

그런데 **필요한 것은 prefill matrix가 아니다.** 알고 싶은 것은 "새로 생성되는 토큰이 context의 어느 구간을 참조하는가"이고, 이는 decode 단계의 query 한 행에 담긴다.

```
decode 한 단계, 한 층:  1 × 16,384 × 28 heads × 2 bytes ≈ 0.9 MB
```

따라서 `AttentionInterface`에 **query 길이에 따라 분기하는 attention 함수**를 등록한다.

```
q_len > 1  (prefill) → SDPA / FlashAttention에 위임, attention 값 미계산
q_len == 1 (decode)  → 명시적 softmax 계산
                        구간별 합으로 즉시 축약
                        축약값만 저장, 원본 폐기
```

이 방식은 prefill 메모리 폭증을 회피하며, `output_attentions=True`를 켤 필요가 없으므로 FlashAttention 비호환 문제도 발생하지 않는다.

**검증:** 짧은 시퀀스(512 토큰)에서 전 구간 eager 실행 결과와 수치가 일치하는지 확인한다. prefill과 decode에서 다른 커널을 쓰므로 필수다.

> **참고 — `generate()`의 반환 구조**
> 소규모 검증에서 `output_attentions=True`를 쓸 경우, `outputs.attentions`는 층 개수만큼의 tensor tuple이 아니라 **생성 단계마다 층별 tensor를 담은 이중 tuple**이다.
> ```
> outputs.attentions[step][layer] → tensor
> step == 0 (prefill): (batch, heads, input_len, input_len)
> step >  0 (decode):  (batch, heads, 1, past_len + 1)
> ```

### 3.5 준수 성향을 어떻게 점수화하는가

개입 실험에서는 이진 판정으로 신호가 너무 거칠다. 연속 점수가 필요하다.

**단일 토큰 logit 차이를 주 지표로 쓸 수 없는 이유**

`getUserData`와 `get_user_data`가 반드시 한 토큰에서 갈린다는 보장이 없다. tokenizer에 따라 여러 토큰에 걸쳐 다를 수 있고, 첫 분기 위치도 이름마다 다르다.

**주 지표 — 준수 선호 점수**

```
준수 선호 점수 = (1/|Y_c|)·log P(Y_c | X) − (1/|Y_v|)·log P(Y_v | X)

Y_c : 준수 표기 후보    Y_v : 위반 표기 후보
X   : 결정 지점까지의 context
```

각 후보의 로그 확률은 teacher forcing으로 계산한다.

**후보는 조건 공통의 사전 고정 후보를 쓴다**

후보를 "모델이 실제로 생성한 함수명"에서 뽑으면 심각한 문제가 생긴다. 조건마다 모델이 다른 이름을 만들어내므로, **조건 간 준수 선호 점수 차이가 선호의 차이인지 채점 대상 문자열의 차이인지 구분할 수 없다.**

따라서 다음과 같이 한다.

```
후보 쌍은 실행 전에 명세로부터 결정하고,
모든 조건에서 동일한 두 문자열을 채점한다.

명세 슬롯 k  →  Y_c = "getUserOrders"
                Y_v = "get_user_orders"
                (V0, V1, V2, V3 전 조건에서 동일)
```

- 후보 쌍은 명세 문구에서 기계적으로 생성한 뒤 연구자가 검수해 고정한다
- 모델이 실제로 무엇을 생성했는지와 무관하게, 고정된 두 후보의 로그 확률만 잰다
- 이렇게 하면 준수 선호 점수가 **동일 문자열에 대한 선호도**를 재게 되어 조건 간 비교가 성립한다

모델이 실제로 생성한 이름은 별도로 기록해 행동 수준 준수 판정에 사용한다. 두 측정은 분리된다.

**보조 지표 — 단일 토큰 logit 차이**

두 후보를 tokenize해 **정확히 한 토큰에서 갈리는 사례에 한해** 해당 위치의 logit 차이를 보조로 보고한다. 해당 조건을 만족하는 비율도 함께 보고한다.

**길이 정규화의 한계**

길이 정규화 로그 확률 비교는 짧은 후보를 선호하는 편향이 알려져 있다. 정규화하지 않은 로그 확률 차이도 함께 보고하고, 두 지표가 같은 방향의 결론을 주는지 확인한다.

### 3.6 attention을 어떻게 개입하는가

#### 무엇을 교체할 수 있는가

attention block의 출력은 모든 source token 정보가 합쳐진 벡터다. "지침 구간만 교체한다"는 그 자체로는 정의되지 않는다.

층 `l`, query head `h`, query 위치 `t`에 대해:

```
head 출력:        z_t^(l,h) = Σ_i α_{t,i}^(l,h) · v_i^(l,h)
구간 S의 기여분:  c_S^(l,h)(t) = Σ_{i∈S} α_{t,i}^(l,h) · v_i^(l,h)
```

context를 네 구간으로 분할한다.

```
I : 지침 구간
C : 선행 코드 구간 (준수 또는 위반)
R : 나머지 (system prompt, 작업 설명)
G : teacher forcing으로 흘려 넣은 후보 토큰 (개입 대상 아님)

z_t = c_I + c_C + c_R + c_G
```

구간 교체의 정의:

```
z_patched = z_corrupted − c_S,corrupted + c_S,clean
```

**적용 위치:** 교체는 **query head 단위로, `W_O` 적용 이전의 head 출력 공간**에서 수행한다. 이후 head를 concat하고 `W_O`를 적용한다. `W_O`가 선형이라 수학적으로는 출력 공간에서 교체해도 같지만, head별 slice를 정확히 다뤄야 하므로 pre-`W_O`에서 명시적으로 처리한다.

**질량 보존:** 구간을 교체하면 attention 총합이 1이 아니게 될 수 있다. 두 변형을 보고하되 **질량 보존 변형을 주 결과**로 삼는다. 총량 변화가 아니라 배분 변화의 효과를 분리하기 위해서다.

- 비보존 — 그대로 교체. 총 질량 변화량을 공변량으로 기록
- 질량 보존 — 교체 후 나머지 구간을 `(1 − m_S^clean)/(1 − m_S^corrupted)`로 재조정

#### GQA에 따른 개입 단위

Qwen2.5-Coder는 GQA를 사용한다. query head 28개가 KV head 4개를 공유하며, 한 KV head를 7개 query head가 함께 쓴다(7B 기준).

> **실제 실행 모델은 3B**(Step 1 게이트 통과 최소 크기): query head 16 / KV head 2, 한 KV head를
> query head 8개가 공유(8:1). 아래 표의 "28/4/7:1"은 7B 기준값이고, 3B 실행은 "16/2/8:1"이다.
> head 수는 `config.json`에서 읽으므로 코드는 크기 무관하며, **개입 단위 원칙(P1a=KV group, 나머지=query
> head)은 모델 크기와 무관**하게 동일하다.

**이 구조가 개입 단위를 결정한다.**

| 개입 | 조작 대상 | 최소 단위 | 층당 단위 수 |
|---|---|---|---|
| **P1a** | K/V 자체를 치환 | **KV group** | 4 |
| **P1b, P3** | head 출력 공간의 기여분 `c_S` | query head | 28 |
| **P2** | attention 가중치 `α` | query head | 28 |

**P1a가 KV group 단위인 이유:** K/V는 group 내 query head들이 공유하므로, 특정 query head 하나만을 위해 K/V를 바꿀 수 없다. K/V를 치환하면 **그 group에 속한 7개 query head 전부가 동시에 영향을 받는다.** 따라서 P1a의 head 수준 순회는 query head 28개가 아니라 **KV group 4개**에 대해 수행한다.

`c_S`나 `α`는 query head마다 독립적으로 존재하므로 P1b·P2·P3는 query head 단위 개입이 가능하다.

이 차이를 무시하고 "head별 개입"이라고 뭉뚱그리면, P1a에서 실제로는 7개 head를 동시에 건드리면서 1개 head를 건드린 것처럼 보고하게 된다. 결과 해석이 달라지므로 모든 보고에서 단위를 명시한다.

#### 지침 구간을 교체하는 것은 대부분 무의미하다

causal mask 때문에 **지침 토큰의 hidden state와 K/V는 자기보다 뒤에 오는 토큰을 볼 수 없다.**

```
[system prompt] → [지침 I] → [선행 코드 C] → [결정 지점 t]
                     ↑             ↑
              두 조건에서 동일    두 조건에서 다름
```

준수 조건과 위반 조건에서 지침 텍스트와 그 앞 context가 동일하다면, **지침 토큰의 K/V는 두 조건에서 비트 단위로 같다.** 지침 K/V를 교체하는 개입은 문자 그대로 아무 변화도 만들지 않는다.

두 조건에서 실제로 달라지는 것은 둘뿐이다.

1. **선행 코드 구간의 K/V** — 준수 코드냐 위반 코드냐에 따라 실제로 다르다
2. **결정 지점의 query** — 앞의 코드를 읽고 만들어지므로 다르다. 그 결과 지침 구간에 대한 `α_{t,i}`도 달라진다

지침 구간의 `v_i`는 동일하므로, `c_I`가 조건 간에 다른 이유는 **오직 `α` 때문이다.** 이 점이 개입 설계를 결정한다.

#### 네 가지 개입

**P1a (주 개입) — query 고정 K/V 치환 · KV group 단위**

```
c_C, cleanKV | q_corr
    = Σ_{i∈C} softmax( q_corr · K_clean^T )_i · V_clean,i
```

query는 위반 실행의 것을 유지하고, 코드 구간의 key/value만 준수 실행의 것으로 바꾼 뒤 attention 점수를 다시 계산한다.

**해석상 주의:** 이것은 완전한 반사실이 아니다. corrupted query와 clean K/V의 결합은 **모델이 자연적으로 생성하지 않는 hybrid activation**이다.

> P1a는 corrupted query를 유지한 상태에서 clean 코드 구간의 K/V를 국소적으로 이식한 hybrid intervention이다.

완전한 반사실이라면 코드 구간 변경이 이후 모든 층·모든 위치로 전파되어야 하지만, P1a는 지정한 층의 지정한 구간에만 개입한다. 따라서 답하는 것은 "이 층의 이 구간이 결정에 기여하는가"이지 "코드가 달랐다면 결과가 어땠을까"가 아니다.

**softmax 범위:** 코드 구간 key를 바꾸면 그 구간 점수가 달라지고 softmax 분모가 바뀌므로 지침·나머지 구간 가중치도 함께 변한다.
- 전체 재계산(주 결과) — 전 구간 softmax 재계산. 질량의 자연스러운 재배분까지 포함
- 질량 고정(보조) — 코드 구간 내부에서만 재정규화. 코드 내용 변화만 분리

**P2 (보조 개입) — 지침 구간 attention 배율 조정 · query head 단위**

지침 구간의 `v_i`가 동일하므로 `c_I` 조작은 곧 `α` 조작이다. 다른 실행의 값을 가져오지 않고 **위반 조건 내부에서만** 조정한다.

```
α'_{t,i} = λ · α_{t,i}   (i ∈ I),   이후 전체 재정규화
λ ∈ {0.5, 1, 2, 4, 8}
```

다른 실행의 정보를 전혀 가져오지 않으며, λ를 여러 값으로 두어 **양-반응 곡선**을 얻는다. 단조 증가하면 증거가 강해진다. PASTA(Zhang et al., ICLR 2024)의 attention steering과 같은 계열이다.

**P1b (탐색적) — 코드 구간 기여분 이식 · query head 단위**

```
z_patched = z_corrupted − c_C,corrupted + c_C,clean
```

구현이 단순하나, **준수 조건에서 형성된 코드 구간의 전체 attention contribution을 이식하는 복합 개입**이다. 준수 조건 query로 계산된 가중치가 함께 들어오므로 "코드 내용만 바꾼 효과"로 읽어서는 안 된다. P1a와 방향이 일치하는지 확인하는 용도다.

**P3 (탐색적) — 지침 구간 기여분 교차 교체 · query head 단위**

```
z_patched = z_corrupted − c_I,corrupted + c_I,clean
```

`c_I,clean`은 준수 조건 query로 계산된 가중치를 담으므로, 지침 표현만 옮기는 것이 아니라 **준수 조건 query의 정보를 함께 들여오는 복합 개입**이다. "지침 표현 자체를 복원했다"고 해석해서는 안 된다.

#### 개입을 어느 토큰 위치에 적용하는가

준수 선호 점수는 후보 함수명 전체의 로그 확률로 계산되는데 개입 수식은 query 위치 하나만 정의한다. 이 불일치를 다음과 같이 해소한다.

> **각 후보 함수명의 모든 teacher-forcing step에서 동일한 층·구간 개입을 적용하고, 그렇게 수정된 logits로 sequence 수준 준수 선호 점수를 계산한다.**

후보 `Y_c = (y_1, ..., y_n)`을 흘릴 때 각 step `k = 1..n`의 query 위치마다 같은 개입을 반복한다. 위반 후보 `Y_v`에도 동일하게 적용한다.

이미 흘린 후보 토큰들은 구간 `G`로 분리하고 개입 대상에서 제외한다. 조작 대상이 아니라 준수 선호 점수 계산을 위해 인위적으로 넣은 토큰이기 때문이다.

**보조 비교:** 첫 토큰 위치에만 개입한 변형도 실행해, 효과가 전 구간 반복에 의존하는지 확인한다.

#### 개입 실험 전용 pair 구성

행동 실험에서는 prefix 토큰 길이 차이를 공변량으로 보정하면 되지만, **activation을 직접 교체할 때는 1토큰 차이도 허용되지 않는다.** 토큰 수가 다르면 결정 지점까지의 위치 인덱스가 어긋나고 RoPE 위치 표현이 달라져 K/V 교체가 정의되지 않는다.

```
구성 절차 (전부 준수 선호 점수를 보기 전에 확정한다):
1. 명세에서 함수명 후보 쌍을 기계적으로 생성
2. 두 표기를 tokenize해 토큰 수가 같은 쌍만 선별
3. prefix 내 나머지 코드는 두 조건에서 동일 문자열로 고정
4. 결정 지점 인덱스가 두 조건에서 같은지 검증
5. 최종 목록을 사전 등록하고 이후 변경하지 않는다
```

**선별 표본의 편향 확인**

토큰 수가 정확히 일치하는 함수명만 고르면 일반적인 함수명과 성질이 다른 특수 표본이 될 수 있다.

- **분포 비교** — 전체 후보와 선별된 후보의 문자 길이, 단어 수, 어휘 빈도, 함수 난이도 분포를 비교해 보고한다
- **결론 범위 제한** — 인과 개입 결론은 "토큰 수가 일치하는 이름 규칙 사례"에 한정된다고 명시한다

#### 개입 효과를 어떻게 판정하는가

**표본 선별에 준수 선호 점수를 사용하지 않는다**

`기저 준수 선호 점수 변화량 = 정상본 준수 선호 점수 − 손상본 준수 선호 점수`가 양수인 pair만 골라 개입하면, **결과 변수를 보고 표본을 고르는 것**이 된다. 이렇게 하면 두 문제가 생긴다.

- 조건 간 차이가 선별에 의해 보장되므로, "차이가 있었다"는 확인이 순환 논증이 된다
- 극단값이 뽑히므로 평균 회귀만으로도 개입 후 값이 중앙으로 이동하며, 이것이 회복으로 오독된다

따라서 다음 원칙을 따른다.

```
표본 선별 기준 = 토큰 수 일치, 함수명 속성, 명세 슬롯
                 (준수 선호 점수 값과 무관한 사전 기준만 사용)

기저 준수 선호 점수 변화량   = 사전 등록된 전체 표본에 대해 집계 수준으로 보고
              (pair 단위 필터로 사용하지 않는다)
```

`기저 준수 선호 점수 변화량`이 전체 표본에서 0에 가까우면 되돌릴 효과가 없다는 뜻이므로, **표본 전체에 대한 판단으로** 개입 실험을 중단한다. 개별 pair를 골라내지는 않는다.

**표본 분할**

Recovery Ratio의 분모에 쓰이는 `기저 준수 선호 점수 변화량`을 같은 표본에서 추정하면 분자와 분모가 상관되어 비율이 왜곡된다. 이를 피하기 위해 사전 등록된 표본을 무작위로 둘로 나눈다.

```
분할 A (50쌍)  →  기저 준수 선호 점수 변화량 추정 전용
분할 B (50쌍)  →  개입 실행 및 준수 선호 점수 변화량 측정
Recovery Ratio = 분할 B의 준수 선호 점수 변화량 ÷ 분할 A에서 추정한 기저 준수 선호 점수 변화량
```

**주 지표와 보조 지표**

| 지표 | 정의 | 역할 |
|---|---|---|
| **준수 선호 점수 변화량** | `개입본 준수 선호 점수 − 손상본 준수 선호 점수` | **주 지표.** 선별 없이 전체 표본에서 계산 |
| Recovery Ratio | 분할 B의 준수 선호 점수 변화량 ÷ 분할 A의 기저 준수 선호 점수 변화량 | 보조. 효과 크기의 해석을 돕는 용도 |

Recovery Ratio가 1을 크게 초과하면 과잉 개입일 수 있으므로 별도 검토한다.

**음성 대조 개입**

`준수 선호 점수 변화량 > 0`이 나와도 "준수 K/V를 넣어서 회복된 것"이 아니라 "어떤 activation이든 크게 건드리면 준수 선호 점수가 흔들린 것"일 가능성이 남는다. 다음 대조에서는 효과가 나타나지 **않아야** 한다.

| 대조 개입 | 내용 | 기대 |
|---|---|---|
| **No-op patch** | 위반 조건 K/V를 같은 위반 조건 값으로 재삽입 | 준수 선호 점수 변화량 ≈ 0. 파이프라인 정확성 검증도 겸함 |
| **무관 구간 patch** | 같은 토큰 길이의 무관한 코드 구간 K/V 삽입 | 준수 선호 점수 변화량 ≈ 0 |
| **R 구간 patch** | 코드가 아닌 나머지 구간 교체 | 준수 선호 점수 변화량 ≈ 0 |
| **무작위 단위 patch** | 무작위 층·무작위 KV group에 무작위 구간 개입 | 준수 선호 점수 변화량 분포가 0을 중심으로 형성 |

무작위 개입의 준수 선호 점수 변화량 분포를 **귀무분포**로 삼아, P1a 값이 상위 꼬리에 위치하는지 검정한다. 이것이 개입 결과 판정의 주 기준이다.

#### 층별·단위별 순회

P1a는 모든 층 × 4개 KV group, P2는 모든 층 × 28개 query head에 대해 순회한다. 음성 대조도 동일 범위에서 실행해 비교가 가능하게 한다.

### 3.7 attention 측정 지표

**길이 정규화의 필요성**

단순 attention 합 비율은 지침 길이가 고정이고 context 길이는 늘어나므로, 모델의 참조 정도와 무관하게 자동 감소한다. 선행 코드 지표는 반대로 자동 증가한다.

```
지침 참조 비율 = (지침 구간 attention 합 ÷ 지침 토큰 수)
     ÷ (전체 attention 합 ÷ 전체 토큰 수)
```

- 지침 참조 비율 = 1 → 지침 토큰이 평균 수준의 attention을 받음
- 지침 참조 비율 > 1 → 평균보다 많이 참조됨

**핵심 성질:** attention이 균등 분포일 때 지침 참조 비율은 context 길이와 무관하게 1이다. "지침 구간이 짧아서 나온 결과"라는 반론이 차단된다.

동일 방식으로 선행 코드 참조 비율, 위반 코드 참조 비율을 정의한다.

**보조 검증 — 동일 길이 구간 대조**

지침 구간과 같은 토큰 수를 가진 코드 구간을 무작위로 100회 추출해 attention 합을 직접 비교한다. 길이가 같으므로 정규화가 불필요하다.

**교란 통제**

| 요인 | 근거 | 처리 |
|---|---|---|
| attention sink | Xiao et al., ICLR 2024 | 앞 4개 토큰 제외. 제외 여부 민감도를 부록에 보고 |
| 위치 편향 | Liu et al., TACL 2024 | 지침을 모든 조건에서 동일 위치에 고정. 조건 간 prefix 길이를 토큰 수준에서 정렬 |

**해석 범위 제한**

Jain & Wallace(NAACL 2019), Serrano & Smith(ACL 2019)가 지적하듯 attention 크기는 출력에 미친 영향력과 같지 않다. 본 연구는 지침 참조 비율을 "모델이 그 구간에 attention을 얼마나 배분했는가"로만 해석하며, 이것만으로 원인을 주장하지 않는다. 인과 주장은 전적으로 3단계 개입에 근거한다.

보완 지표로 Kobayashi et al.(EMNLP 2020)의 `‖α · v‖`를 함께 계산한다. attention이 높아도 value가 작으면 실제 기여가 작다는 점을 반영한다.

## 4. 실험 가설

### 1단계 — 행동 수준 (주 가설)

**H1.** context 내 위반 코드 비율이 높을수록 다음 함수의 준수율이 낮다.
- H1a (주 가설): 위반 3개 조건의 준수율 < 위반 0개 조건의 준수율
- H1b: 위반 개수(0, 1, 2, 3)에 따라 준수 odds가 단조 감소한다

**H2.** context에 누적된 선행 코드의 스타일이 이후 함수의 준수율에 영향을 준다.
- H2a (주 가설): Violation-style 조건의 준수율 < Compliant-style 조건의 준수율. 두 조건은 기능·작업·API가 동일하고 표기만 다르므로 순수한 스타일 효과다
- H2b: Compliant-style과 Neutral의 차이는 작업 관련 코드가 참조를 끌어당기는 효과를 나타낸다. 방향은 사전에 예측하지 않는다
- H2c: 지침이 선행 코드보다 뒤에 오는 경우(After)가 앞에 오는 경우(Before)보다 준수율이 낮다

**H3 (규칙 등급 비대칭, H2 내부에서만 검정).** Gamage(2026)의 omission/commission 비대칭이 성립한다면, H2 하네스 안에서 **금지형 규칙(등급 C)의 선행 코드 패턴 효과가 수행형 규칙(등급 B)보다 크다.**

**H4 (프런티어 재현).** 위 행동 효과가 프런티어 모델에서도 같은 방향으로 나타난다.

### 2단계 — 관측 수준

**H5.** 위반 코드가 포함된 조건에서 지침 참조 비율이 더 낮다.

**H6.** Violation-style 조건에서 선행 코드 참조 비율이 Compliant-style 조건보다 높다.

### 3단계 — 개입 수준

**H7 (P1a).** query를 위반 조건 값으로 고정한 채 코드 구간의 K/V를 준수 조건 값으로 치환하면, 준수 선호 점수 변화량이 무작위 개입의 귀무분포 상위 꼬리에 위치한다.

**H8 (P2).** 지침 구간 attention 배율 `λ`를 높이면 준수 선호 점수가 단조 상승한다. 음성 대조에서는 이 단조성이 나타나지 않는다.

## 5. 실험 환경

### 5.1 모델 구성 — 왜 두 계열을 함께 쓰는가

행동 실험은 **prefix를 조작하고 준수율을 재는 것뿐이므로 가중치 접근이 필요 없다.** API만 있으면 프런티어 모델에서도 그대로 돌아간다. 가중치가 필요한 것은 attention 관측과 개입뿐이다.

| 계열 | 모델 | 담당 | 이유 |
|---|---|---|---|
| **프런티어** | Claude Sonnet, GPT 계열 (API) | 행동 효과의 외적 타당도 | McMillan의 관찰이 이루어진 급. 실제 사용 환경과 일치 |
| **오픈 가중치** | Qwen2.5-Coder-7B (주), 14B·32B (규모 확인) | 행동 + attention 관측 + 개입 | 내부 접근 가능. dense 구조라 구간별 기여 분해가 성립 |

```
프런티어에서 행동 효과 확인
        ↓ (같은 조작, 같은 측정)
오픈 모델에서 같은 행동 효과 재현
        ↓ (여기서만 가능)
오픈 모델에서 메커니즘 분석
```

두 계열에서 행동 효과의 방향과 크기가 일치하면, 오픈 모델의 메커니즘 분석을 프런티어에 대한 가설로 제시할 근거가 생긴다. 일치하지 않으면 메커니즘 분석의 적용 범위가 오픈 모델로 한정된다는 것을 명확히 보고한다.

**프런티어 실험 범위 (비용 제약)**

| 항목 | 범위 |
|---|---|
| 실험 1 | V0 vs V3 (양 극단만) |
| 실험 2 | Violation / Compliant / Neutral, 지침 시점 Before만 |
| 규칙 | 등급 A(H1) + 등급 B·C(H2) |
| 측정 | 조작 직후 첫 번째 함수만 |
| 모델 | Claude Sonnet 계열 1종 + GPT 계열 1종 |

프런티어 모델은 버전이 수시로 바뀌므로 세션마다 모델 문자열과 실행 일자를 기록하고, 도중 변경 시 그 시점을 보고한다.

### 5.2 하네스와 실행 환경

| 항목 | H1 (명세 기반 생성) | H2 (파일 편집 agentic) |
|---|---|---|
| 대상 등급 | A, B | B, C |
| 도구 | 없음 | read, write, bash |
| 측정 | 준수 판정 + attention + 개입 | 준수 판정만 (git diff) |
| 저장소 구조 | 일반 | `vendor/`, `migrations/`, 외부 기여 모듈 배치 |
| 변동성 | 낮음 | 높음 (완주율 관리 필요) |

공통 설정

| 항목 | 값 |
|---|---|
| attention 수집 | `AttentionInterface` 조건부 함수 (H1 전용) |
| context 상한 | 16K 토큰 |
| 대상 코드 | Python 2개(FastAPI, Flask), TypeScript 1개(Next.js) |

### 5.3 무작위성과 배정 설계

동일 모델·동일 prompt·greedy decoding이면 세션을 수백 번 돌려도 사실상 같은 결과의 반복이며, 표본 수는 늘어도 정보량은 늘지 않는다.

**디코딩 설정**

| 항목 | 값 | 이유 |
|---|---|---|
| 방식 | temperature sampling | 세션 간 변동의 주 출처 |
| temperature | 0.7 | 파일럿에서 분산이 지나치게 크면 0.4로 하향 |
| top-p | 0.95 | |
| seed | 세션마다 고유 seed 기록 | 재현 가능성 |

greedy 세션도 조건당 20건 별도 수집해, sampling 없이도 조건 간 차이가 나타나는지 확인한다.

**생성물 고정**

- 함수 명세 목록은 저장소 기존 모듈에서 추출한 뒤 검수해 고정한다. 조건 간 동일한 목록을 쓴다
- prefix 코드는 명세에서 파생해 연구자가 작성하며, 조건별 변형은 표기 규칙만 기계적으로 치환해 생성한다
- **준수 선호 점수 후보 쌍은 명세에서 사전 생성해 고정하고, 모든 조건에서 동일한 문자열을 채점한다**

**배정 설계**

- **블록 무작위화** — 동일 작업 내에서 조건을 블록으로 묶어 배정한다
- **대응 설계** — 같은 작업·같은 seed를 조건 간에 공유한다. seed `s`와 작업 `j`의 조합에 대해 V0~V3를 모두 실행한다. 조건 간 비교가 대응표본이 되어 검정력이 오르고, 작업·seed 변동이 상쇄된다

### 5.4 왜 전체 SWE 작업을 쓰지 않는가 (H1)

mini-SWE-agent로 실제 SWE 작업을 완주시키면 두 문제가 생긴다.

- **완주율** — 7B급은 agentic 작업 실패율이 높아 데이터가 모이지 않는다
- **교란** — 작업마다 탐색 경로, 도구 호출 횟수, 실패-재시도 패턴이 달라 조작 효과를 덮는다

H1은 이 변동을 제거하기 위해 명세 기반 루프를 쓴다. 대신 실제 사용 환경과 거리가 있다(한계 8.5).

H2는 금지형 규칙 때문에 파일 편집이 불가피하므로 agentic 환경을 쓰되, 작업 범위를 좁혀 완주율을 관리한다.

보조로 mini-SWE-agent 기반 세션 50건을 별도 수집해, H1의 효과 방향이 실제 에이전트 환경에서도 나타나는지 확인한다.

### 5.5 파일럿 통과 조건

본 실험 착수 전 다음을 확인한다. 하나라도 미달이면 설계를 수정한다.

| 항목 | 기준 | 미달 시 대응 |
|---|---|---|
| 기저 준수율 (H1) | 55% ~ 85% | 14B → 32B 상향. 그래도 미달이면 지침 난이도 조정 |
| 기저 준수율 (H2, 등급 C) | 55% ~ 85% | 작업 설계 조정 |
| 세션당 소요 시간 | 전체 세션 수 × 시간이 실행 가능 범위 | 검정력 분석 결과까지 세션 수 축소 |
| H1 완주율 | 95% 이상 | 명세 개수·난이도 하향 |
| H2 완주율 | 80% 이상 | 작업 범위 축소 |
| 위반 기회 비율 (등급 C) | 70% 이상 | 최단 경로가 금지 파일 수정이 되도록 명세 조정 |

**기저 준수율 기준의 근거:** 너무 높으면(>85%) 낮출 여지가 없어 천장 효과가 발생하고, 너무 낮으면(<55%) 신호가 노이즈에 묻힌다.

## 6. 실험 설계

### 6.1 실험 1 — context 내 위반 코드 (H1 하네스)

**설계:** prefix 내 위반 함수 개수를 무작위 배정하는 4수준 설계

| 조건 | prefix 함수 4개 중 위반 개수 |
|---|---|
| V0 | 0 |
| V1 | 1 |
| V2 | 2 |
| V3 | 3 |

**prefix 구성 원칙**

- 네 조건의 prefix는 **기능이 완전히 동일한 코드**로 구성한다. 규칙 준수 여부만 다르다
- 위반 함수의 위치는 prefix 내에서 무작위화한다
- **토큰 길이 처리:** 행동 실험은 주석 길이 조정으로 ±3 토큰 이내로 맞추고 잔여 차이를 공변량으로 포함한다. **개입 실험에는 이 허용 오차를 적용하지 않으며, 결정 지점까지 토큰 수가 정확히 일치하는 전용 pair를 별도 구성한다(3.6)**

**지침 종류 (세션마다 무작위 배정)**

| 등급 | 규칙 | 역할 |
|---|---|---|
| A | 모든 함수 이름을 camelCase로 작성 | 행동 + 개입 실험 |
| B | 모든 함수에 docstring 포함 | 행동 (H1 내부 참조용) |

**측정 — 직접효과와 연쇄효과의 분리**

prefix 이후 함수 3개를 순차 생성하면 첫 번째 결과가 두 번째·세 번째의 context에 다시 들어간다.

```
prefix 조작 → 함수 1 → 함수 2 → 함수 3
                  ↑        ↑
            새로 생성된 코드가 다시 매개변수로 작용
```

| 구분 | 대상 | 해석 |
|---|---|---|
| **주 결과** | 조작 직후 **첫 번째 함수** | prefix의 순수 직접효과 |
| 보조 결과 | 두 번째·세 번째 함수 | 효과가 증폭되는지 감쇠되는지 |

통계 모형에 **조건 × 후속 함수 순서 상호작용**을 포함한다. 주 가설 검정은 첫 번째 함수만으로 수행한다.

**위약 지침 조건 (attention 지표 대조용)**

지침이 없으면 지침 구간 attention을 계산할 수 없다. "지침 없음" 대신 **토큰 수가 같고 행동 지시가 없는 문장**을 같은 위치에 넣는다.

```
실제 지침:
  "All function names must be written in camelCase.
   This convention applies to every function you create in this project."

위약 (토큰 수 ±2 이내):
  "This project was migrated from an earlier repository layout.
   Historical release notes are archived in the docs folder for reference."
```

**위약 중립성의 검증 방법**

`p > .05`는 두 조건이 같다는 증거가 아니라 차이를 찾지 못했다는 뜻일 뿐이다. 따라서 **동등성 검정(TOST)**을 사용한다.

```
사전 지정 허용 범위:  준수율 차이 ±5%p
귀무가설:            |위약 − 지침없음| ≥ 5%p
대립가설:            |위약 − 지침없음| < 5%p
```

두 경계 모두에서 기각되면 동등성이 확립된다. 허용 범위는 실험 1에서 검출하려는 최소 효과 크기보다 충분히 작게 잡은 값이며 파일럿 이전에 사전 등록한다. 확립되지 않으면 위약 문구를 재설계하고 다시 검정한다.

### 6.2 실험 2 — 선행 코드 스타일 × 지침 제시 시점 (H1 하네스)

**설계:** 3 (선행 코드 스타일) × 2 (지침 제시 시점) 요인 설계

| 선행 코드 스타일 | 내용 |
|---|---|
| **Compliant-style** | 동일 기능·동일 작업 코드, 지침을 지킨 표기 |
| **Violation-style** | 동일 기능·동일 작업 코드, 지침을 어긴 표기 |
| **Neutral** | 동일 토큰 길이의 무관한 코드 |

| 지침 제시 시점 | 내용 |
|---|---|
| **Before** | 지침이 선행 코드보다 앞 |
| **After** | 선행 코드가 먼저, 지침이 뒤 |

**왜 세 스타일 조건이 모두 필요한가**

Violation-style과 Neutral만 비교하면 두 조건이 스타일 외에도 여러 면에서 다르다. 현재 작업과의 관련성, 함수의 의미, 변수명과 API, 앞뒤 코드의 연결성이 모두 다르다. 이 상태에서는 준수율 차이가 나와도 **선행 스타일 때문인지, 작업 관련 코드가 더 강하게 참조되기 때문인지 구분할 수 없다.**

```
Violation-style vs Compliant-style
  → 관련성·의미·API 동일, 표기만 다름 → 순수 스타일 효과

Compliant-style vs Neutral
  → 스타일은 둘 다 지침과 일치, 작업 관련성만 다름
  → 작업 관련 코드가 참조를 끌어당기는 효과
```

**선행 코드 구성 원칙**

- Compliant-style과 Violation-style은 **동일한 함수 4개**를 표기만 바꾸어 만든다. 함수 의미, 변수명, API, 주석 내용이 모두 같다
- Neutral 코드는 두 조건의 평균 토큰 수에 맞춘다
- 세 조건의 토큰 수를 ±3 이내로 정렬하고 잔여 차이를 공변량으로 포함한다

**보조 조건 — 선행 코드 출처에 따른 차이**

Violation-style 선행 코드를 (a) 연구자 작성 고정 스크립트로 넣은 경우와 (b) 같은 모델이 지침 없이 실제 생성한 코드를 넣은 경우로 나눠 비교한다(각 40세션). 모델은 출처를 알 수 없지만, 모델이 생성한 코드는 통계적 성질이 다를 수 있다.

이 비교는 "자기 생성 여부를 모델이 인식하는가"를 묻는 것이 아니라 **선행 코드의 분포 특성이 결과를 바꾸는가**를 확인하는 것이다.

### 6.3 실험 3 — 규칙 등급 비대칭 (H2 하네스)

**목적:** 금지형 규칙과 수행형 규칙에서 선행 코드 패턴 효과의 크기가 다른지 확인

**설계:** 2 (규칙 등급) × 2 (prefix 스타일)

| 요인 | 수준 |
|---|---|
| 규칙 등급 | B (수행형: docstring 필수 / logging만 사용) · C (금지형: `vendor/` 수정 금지 / `migrations/` 수정 금지) |
| prefix 스타일 | Compliant (규칙을 지킨 이전 작업 기록) · Violation (규칙을 어긴 이전 작업 기록) |

**등급 C의 prefix 구성**

위반 prefix에는 금지된 경로의 파일을 직접 수정한 이전 작업 기록(diff 또는 수정된 파일 내용)을 포함한다. 준수 prefix에는 같은 목적을 wrapper로 달성한 기록을 넣는다. 두 조건의 기능은 동일하다.

**작업 설계**

```
요건:
  - 목표 달성의 최단 경로가 금지된 파일 수정
  - 규칙을 지키는 우회 경로(wrapper, 상속, 설정 주입)도 존재

예: vendor/http_client.py의 기본 타임아웃을 30초로 변경
    → 직접 수정은 금지, wrapper 작성이 준수 경로
```

**기회 통제:** 세션마다 "금지된 수정이 최단 경로였는지"를 기록하고, 기회가 없었던 세션은 분석에서 제외한다. 제외 비율을 보고한다.

**비교의 범위:** 등급 B와 C의 비교는 **이 하네스 내부에서만** 수행한다. H1의 등급 B 결과와 직접 비교하지 않는다.

### 6.4 통계 분석

**표본 비독립성**

한 세션 내 함수들은 같은 모델·작업·context를 공유하므로 독립이 아니다. 이를 무시하면 표준오차가 과소 추정되어 유의하지 않은 결과가 유의하게 보인다.

```
준수 여부 ~ 조건 × 후속함수순서
          + prefix토큰수
          + 저장소                    ← 고정효과
          + (1 | 작업)
          + (1 | 세션)
```

- 일반화 선형 혼합모형(GLMM), logit 연결함수
- 수렴 실패 시 임의효과를 `(1 | 세션)`만 남기거나 세션 수준 군집 강건 표준오차로 대체

**저장소를 고정효과로 두는 이유**

저장소가 3개뿐이다. 임의효과는 해당 수준을 더 큰 모집단의 표본으로 보고 분산을 추정하는데, **3개 수준으로는 분산을 안정적으로 추정할 수 없다.** 수렴 실패나 분산 추정치 0이 흔하다. 저장소는 관심 대상이 아니라 통제 대상이므로 고정효과가 적절하다.

**중첩 구조**

```
저장소 (3개, 고정효과)
  └─ 작업 (저장소마다 여러 개, 임의효과)
       └─ 세션 (작업마다 여러 개, 임의효과)
            └─ 함수 (관측 단위)
```

**대응 설계의 반영**

5.3의 대응 설계에 따라 같은 작업·seed가 조건 간에 공유되므로, `(1 | 작업:seed)` 항을 추가해 대응 구조를 모형에 반영한다. 이 항을 넣은 모형과 뺀 모형을 함께 보고한다.

**하네스 분리**

H1과 H2는 별도 모형으로 적합한다. 하나의 모형에 합치면 하네스 차이가 규칙 등급 효과와 교란된다.

**다중 검정**

사전 등록한 주 가설(H1a, H2a, H3)에만 유의성을 판정하고 나머지는 탐색적으로 보고한다. 주 가설 외 검정에는 Benjamini-Hochberg 보정을 적용한다.

**표본 크기**

파일럿 데이터로 검정력 분석을 수행해 조건당 세션 수를 확정한다. 잠정 목표는 기준 준수율 70%, 검출 목표 odds ratio 0.70, 세션 내 상관 0.2 가정이다. **아래 세션 수는 상한이며 파일럿 결과로 재산정한다.**

| 구성 | 잠정 세션 수 |
|---|---|
| 실험 1 (V0~V3, 등급 A·B) | 480 |
| 실험 1 위약 | 120 |
| 실험 2 (3 스타일 × 2 시점) | 480 |
| 실험 2 보조 (코드 출처) | 80 |
| 실험 3 (H2, 2 등급 × 2 스타일) | 320 |

### 6.5 검증 항목

| 항목 | 방법 | 기준 |
|---|---|---|
| 준수 판정 신뢰도 | 전체 10% 수동 판정 대조 | Cohen's kappa ≥ 0.85 |
| 위약 중립성 | TOST 동등성 검정 (허용 ±5%p) | 두 경계 모두 기각 |

## 8. 한계

**8.1 개입 해석의 한계**

*무엇을 답할 수 있는가* — 개입이 답하는 것은 "선택한 attention component가 행동 효과에 인과적으로 기여하는가"까지다. "전체 효과의 몇 퍼센트가 attention 경로를 지나는가"는 답할 수 없다. 개입이 특정 층·특정 구간에 한정된 국소 조작이기 때문이다.

*개입의 순수성* — P1a는 query를 고정하므로 비교적 깨끗하지만 여전히 hybrid activation이며, P1b와 P3는 준수 조건 query의 정보를 함께 들여오는 복합 개입이다. 이들 결과를 "해당 구간의 표현만 바꾼 효과"로 읽어서는 안 된다.

*층별 개입의 부분성* — 실제 위반 코드는 모든 층에 영향을 미치므로, 위반 실행의 층 `l` query는 이미 앞선 층에서 전파된 효과를 담고 있다. 단일 층 개입은 전체 효과의 일부만 되돌리며, 층별 효과를 합산해 전체 효과로 해석할 수 없다.

*GQA에 따른 해상도 제한* — P1a는 K/V 공유 때문에 KV group 단위로만 개입할 수 있다. 한 group에 query head 7개가 묶여 있으므로, P1a에서는 query head 수준의 국소화가 불가능하다.

*인과와 의미의 간격* — 개입으로 준수 선호 점수가 변한다고 해서 모델이 그 경로를 통해 "지침을 참조했다"는 뜻은 아니다.

**8.2 개입 대상 규칙과 표본의 제한**

준수 선호 점수는 준수/위반 표기가 짝을 이루는 이름 규칙에서만 정의된다. docstring 누락이나 파일 수정 금지는 위반이 여러 토큰에 분산되거나 생성 과정 전반에 걸쳐 결정되므로 후보 쌍을 만들 수 없다.

여기에 더해 개입 실험은 두 표기의 **토큰 수가 정확히 일치하는 함수명**에만 적용된다. 이 부분표본은 전체 함수명 분포와 다를 수 있으며, 분포 비교를 보고하더라도 선별 편향이 완전히 제거되지는 않는다.

**따라서 인과 관련 결론은 "토큰 수가 일치하는 이름 규칙 사례"에 한정된다.**

**8.3 모델 범위**

주 실험은 Qwen2.5-Coder-7B 한 모델이다. 14B/32B는 행동 수준만 확인한다. Llama, DeepSeek 등 다른 계열이나 MoE 구조로의 일반화는 확인되지 않는다. MoE는 expert routing이 개입해 구간별 기여 분해가 성립하지 않는다.

**8.4 프런티어 모델에서의 메커니즘 미검증**

행동 효과는 프런티어에서도 측정하므로 외적 타당도가 확보된다. 그러나 **attention 관측과 개입은 가중치 접근이 필요해 오픈 모델에서만 가능하다.** 메커니즘 결론은 Qwen2.5-Coder 계열에 한정되며, 프런티어에 대해서는 가설로만 제시한다. 같은 행동이 다른 내부 경로에서 나올 가능성은 배제할 수 없다.

프런티어 모델은 버전과 시스템 프롬프트가 공개되지 않고 수시로 바뀌므로 재현 가능성 면에서도 제약이 있다.

**8.5 하네스의 인위성과 하네스 간 비교 불가**

H1의 명세 기반 루프는 실제 에이전트 환경과 다르다. 탐색, 도구 호출, 실패-재시도가 없다. mini-SWE-agent 50세션으로 방향 일치를 확인하지만 완전한 보완은 아니다.

H1과 H2는 환경이 근본적으로 다르므로 두 하네스의 준수율을 직접 비교할 수 없다. 등급 B와 C의 비대칭은 H2 내부에서만 검정하며, 이 결과가 H1 환경에도 적용되는지는 확인할 수 없다.

**8.6 prefix의 인위성**

통제 실험의 prefix는 연구자가 구성한 것이므로, 모델이 실제로 생성하는 코드와 통계적 성질이 다를 수 있다. 실험 2의 코드 출처 비교가 부분적으로 보완하지만 완전하지는 않다.

**8.7 연구 대상의 범위**

모델은 context 내 코드의 출처를 알 수 없으므로, 본 연구가 다루는 것은 "자기 생성 코드의 영향"이 아니라 **"context에 누적된 선행 코드 패턴의 영향"**이다. 실제 에이전트 세션에서는 이 코드가 대부분 모델 자신이 생성한 것이지만, 결과는 출처와 무관한 일반적 진술로 읽어야 한다.

**8.8 토큰화 비대칭**

camelCase와 snake_case의 tokenizer 분해가 달라 행동 실험에서 완전한 길이 일치가 불가능하다. 공변량 보정으로 대응하나 잔여 교란 가능성이 남는다. 준수 선호 점수의 길이 정규화도 짧은 후보를 선호하는 편향이 있어 비정규화 지표를 함께 보고한다.

**8.9 context 길이**

16K 상한을 둔다. 실제 개발의 장기 세션에서의 행동은 확인할 수 없다.

**8.10 지침 종류의 범위**

표기 규약, 수행형, 금지형 세 등급을 다루지만 각 등급 내에서 2개 규칙씩만 사용한다. 아키텍처 수준 지침이나 다단계 절차 지침은 다루지 않는다.

**8.11 기여의 성격**

자기 출력이 이후 생성을 오염시키는 메커니즘 자체는 새롭지 않다. Zhang et al.(ICML 2024)의 hallucination snowballing이 사실 오류 영역에서 같은 구조를 보였다. 본 연구의 기여는 **새로운 현상의 발견이 아니라, 이 메커니즘이 코딩 에이전트의 지침 준수에도 적용되는지를 무작위 배정과 개입 실험으로 검증하는 것**이다. 또한 이 분야의 preprint 발표 속도를 고려하면 유사 연구가 병행 진행 중일 가능성을 배제할 수 없다.
